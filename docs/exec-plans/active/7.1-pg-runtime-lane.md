# 7.1 — `platform/db` pg variant + portable subset audit

## Objective

Give the kit a Postgres runtime lane beside SQLite: a `platform/db` variant backed
by pgx, migrations applied at boot from the pg tree, serializable retry for write
transactions, and the build-tag audit that lets engine-agnostic code compile under
`-tags pg`.

The generated query layer already has its pg half: `internal/db/gen/pg_*.go` is
committed, the pg migrations (`db/migrations/pg/0001`–`0007`) exist, the schema
inventory test holds both trees to the same names, and `sqlc.yaml` overrides the
nullable timestamp columns for both engines. What is missing is the runtime.

## Current state (verified)

- `internal/platform/db` holds **one** implementation, `sqlite.go`: `Database`
  with `SQL()`, `Ping`, `Close`, `InTx(ctx, func(tx Tx) error)`, and
  `Migrate(ctx, fsys)` driving the embedded SQLite migrations.
- `cmd/api` migrates at boot; `cmd/worker` deliberately does not.
- **39 files carry `//go:build !pg`**, including every feature root and repository,
  so the pg lane currently builds only the platform and generated packages.
- `go.mod` has **no pgx**: the lane needs the driver, and `sqlc` generates
  `database/sql`-style code, so the driver belongs behind `platform/db` via
  `pgx`'s `stdlib` adapter rather than in a pgx-native query mode.
- The portability rules already hold: drivers are importable only in
  `platform/db` and `db/gen`, and `db/queries/common/` is the portable query set
  that `sqlc` transpiles per engine (`?` to `$n`).

## Design

**Runtime variant.** `internal/platform/db/pg.go` under `//go:build pg`, with
`sqlite.go` gaining the complementary tag. Same exported surface, so callers do
not branch: `SQL()` returns the `*sql.DB` over the pgx stdlib connector, `Ping`
uses a context with a timeout, `Close` closes the pool, and `Migrate` drives the
pg migrations through the goose provider with the Postgres dialect — the same
in-process model the API already uses, so no operator step is introduced.

**Serializable retry.** `InTx` on the pg lane runs at serializable isolation and
retries the transaction when the server reports a serialization failure
(SQLSTATE `40001`), with a bounded attempt count and jittered backoff. SQLite
serialises writers, so this is the pg lane's half of the ADR-0005 rule; the
SQLite lane keeps its current shape. The retry must only wrap the transaction
body, and the plan records that a caller-supplied function may run more than once
— so it must stay side-effect free outside the transaction.

**Configuration.** A `DATABASE_URL`-style key for the pg lane (name to be settled
against `backend-core-kit`'s convention before it lands), validated at load and
documented in `env.example`. SQLite keeps its file path. The composition roots
choose the lane by build tag, not by config: one binary, one engine.

**Portable subset audit.** Walk the 39 tagged files and sort each into:
- **lifts** — engine-agnostic code: feature roots, repositories, services, and
  handlers, which talk only to `ports` and `gen`;
- **stays** — anything that names a SQLite behaviour (file paths, WAL, the
  migrations embed point, engine-specific tests).
The audit lands as a doc note listing every path with its verdict, so the next
person can see the decision rather than re-derive it, and the tag count is
asserted by a test so it can only shrink deliberately.

**Verification.** Integration tests for the pg lane are guarded by an env URL and
skip when it is absent — the kit has no compose file and CI's dual-lane matrix is
7.2's job — so local runs stay green and the matrix turns them on.

## Acceptance checks

1. `go build -tags pg ./...` compiles with the pg `Database` in place, and the
   SQLite lane is unchanged when the tag is absent (`make build` and `build-pg`
   both green).
2. With a live Postgres URL: migrations apply from the pg tree, a repository
   round trip through `internal/db/gen/pg_*.go` reads what it wrote, and a
   forced serialization conflict is retried rather than surfaced.
3. Without the URL, the pg integration tests skip loudly (`t.Skip`) and never
   silently pass.
4. The audit note exists, every `!pg` path has a verdict, and the count assertion
   matches the tree.
5. `make verify` stays green on the SQLite lane, and 7.3's `make verify-pg` runs
   the same profile against the pg lane once it lands.

## Risks and notes

- **Retry semantics.** A caller's transaction body may execute more than once on
  pg; the platform contract has to say so, and the feature code that already
  passes a closure must not carry side effects outside it. The account-deletion
  finalize is the one to check first: it audits and deletes inside the
  transaction, which is exactly the shape the rule wants.
- **Tag churn.** Lifting `!pg` across 39 files is mechanical but touches every
  feature; doing it in one pass risks mixing engine work with feature work, so the
  plan splits it: the audit note first, the tag lifts second, one feature per
  change.
- **Driver choice.** `pgx` via `stdlib` keeps the generated `database/sql` code
  usable; a pgx-native sqlc mode would regenerate the query layer and is recorded
  as the alternative if the stdlib route proves limiting.
- **No HA or pooling policy in this task.** Connection limits, prepared-statement
  caching, and failover are deployment concerns; this task lands a correct pool
  and the isolation rule, not a tuning.

## Progress — the portable subset audit (2026-10-15)

`docs/engineering/pg-portable-subset.md` records the verdict for every one of the
39 `//go:build !pg` paths: **29 lift** (feature roots, repositories, services,
platform wiring, worker bootstrap), **9 stay** (the generated SQLite query half and
the SQLite `Database` with its integration tests), and **1 switch**
(`cmd/api/main.go`, which must select its embedded migration tree per lane instead
of naming `migrations.SQLite`). `tools/gokit/portable_test.go` asserts those three
counts against the tree, so the tag set can only shrink on purpose — the check
points back at the note when it changes.

Sequencing recorded: the contract tests under `cmd/api` lift by dependency but need
a pg test database, so they keep their tag until 7.2's matrix provisions one.

Still to land: the pgx-backed `Database`, the serializable retry in `InTx`, the
`DATABASE_URL`-style key, the tag lifts one feature at a time, and the guarded pg
integration tests.

## Sequencing note — the driver (2026-10-15)

The lane needs a driver that is not in `go.mod` today: `github.com/jackc/pgx/v5`
is what the plan settles on, reached through its `database/sql` adapter so the
generated query half keeps working, and the registry is reachable (v5.11.0 is the
current release). It must land **in the same change as the runtime**: an imported-
but-unconsumed dependency is exactly what `go mod tidy` removes, and this repository
has already paid that lesson once. The dependency is therefore the first line of the
runtime change, not a separate commit.
