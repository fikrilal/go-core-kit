# 1.8 — Idempotency Middleware

- Status: completed
- Owner: Core kit maintainers
- Risk: medium (write-safety behavior)
- Date: 2026-10-10
- Roadmap: `docs/exec-plans/roadmap.md` task 1.8
- Related ADRs: ADR-0002 (contract parity), ADR-0003 (stdlib HTTP), ADR-0006 (Redis roles)

## Objective

Implement `Idempotency-Key` handling for opted-in routes: Redis lock, cached-response replay with `Idempotency-Replayed: true`, and `409 IDEMPOTENCY_IN_PROGRESS` for concurrent duplicates. Routes opt in via `Router.HandleIdempotent`, enabled by the `WithIdempotency(client)` router option.

## Constraints

- Contract: `Idempotency-Key` accepted on retryable writes; replay sets `Idempotency-Replayed: true`; concurrent duplicates get 409 with `IDEMPOTENCY_IN_PROGRESS`.
- **Missing key = pass through** (no dedup) — parity-safe: clients that never send the header (or backend-core-kit clients that do) behave unchanged.
- **Only 2xx responses are cached.** Failed requests release the lock and are not replayed, so clients can retry the same key after fixing the request.
- **Fail closed** on Redis errors (a write that cannot be made idempotent-safe must not execute silently).
- Lock TTL (30 s) is crash recovery only; the happy path deletes the lock after storing. Response TTL: 24 h.
- No payload fingerprinting/conflict detection in this increment (follow-up if the contract suite requires it).

## Impact Areas

- API / contract: yes (write-safety headers, 409 behavior)
- DB / migrations: no
- Auth / session: no
- Queue / jobs: no
- Config / secrets: no
- Observability: yes (lock/store failures logged)
- CI / release: no

## Acceptance Criteria

1. First request with a key executes the handler; a repeat returns the cached status, body, `Content-Type`, and `Location`, with `Idempotency-Replayed: true`.
2. Different keys run independently; requests without a key pass through unchanged.
3. A concurrent duplicate while the first is in flight returns 409 `IDEMPOTENCY_IN_PROGRESS`.
4. Non-2xx responses are not cached and run again on retry (no replay header).
5. The lock is released after completion (crash recovery is TTL-based).
6. `HandleIdempotent` without configuration panics at startup; `make verify` green.

## Decision Log

- 2026-10-10: Missing `Idempotency-Key` passes through — requiring it would break existing clients; lenient is the compatibility-preserving choice.
- 2026-10-10: Only 2xx responses are cached; error responses release the lock and re-execute on retry. Avoids poisoning a key with a stale error (for example an expired-token 401).
- 2026-10-10: Redis failures on lock/read/store fail the request (500, logged) — idempotency is a write-safety guarantee, not best-effort.
- 2026-10-10: Lock cleanup runs with `context.WithoutCancel` so client disconnects do not leave locks behind for the full TTL.
- 2026-10-10: Key layout is `idempotency:<route pattern>:<key>` with a `:lock` suffix; the route pattern doubles as the scope.

## Completion Notes

Implemented idempotency in `httpx`: the `WithIdempotency(client)` router option and `HandleIdempotent(pattern, handler)` route wrapper (panics without configuration, so wiring mistakes fail at startup). Concurrent duplicates receive 409 `IDEMPOTENCY_IN_PROGRESS`; cached 2xx responses replay with `Idempotency-Replayed: true`, preserving status, body, `Content-Type`, and `Location`. Locks release via `context.WithoutCancel` so disconnected clients never leave locks for the full TTL. Missing keys pass through; non-2xx responses are not cached; Redis failures fail closed (500, logged). `platform/redis` gained `Get`/`Set`/`SetNX`/`Del` with sentinel-aware `Get`. Tests: 7 new httpx cases (incl. a channel-synchronized concurrency case) and 1 new redis case; one `revive` unused-parameter fix during verification.
