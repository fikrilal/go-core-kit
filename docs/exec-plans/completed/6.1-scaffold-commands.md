# 6.1 — `scaffold feature` / `scaffold endpoint`

## Objective

One command scaffolds a feature, and one command scaffolds an endpoint whose
output passes `make verify` untouched — lint, boundary rules, knowledge check,
contract coverage, and tests. This is the mechanism behind Phase 6's exit gate:
a fresh clone can scaffold a working endpoint in one command.

## Constraints the scaffold must respect

- **Contract ownership.** The wire contract is owned by backend-core-kit. An
  endpoint can only be scaffolded for an operation the pinned snapshot already
  declares — the operation id must exist in `contracts/openapi.yaml`, and while
  it is unimplemented it sits in `contracts/allowlist.yaml`. Scaffolding an
  endpoint *implements* that operation, so the scaffold removes it from the
  allowlist; the coverage test then keeps both directions honest.
- **Verify-clean output.** Generated code must satisfy the gates it lands in:
  `httpx` decode/respond helpers (no raw `encoding/json`, no `w.Write`), an
  injected clock for time, repository-only SQL, wrapped errors, exported API doc
  comments, and no dependency-rule violations.
- **No invented contract surface.** `scaffold feature` adds no routes, so it
  cannot move the contract; `scaffold endpoint` refuses an operation that is not
  in the snapshot or that is already implemented.
- **Reversibility.** 6.2 (`remove feature`) unwires whatever the scaffold wires,
  so every wiring edit must be marker-delimited text, not prose the remover has
  to understand.

## Design

CLI (dispatched from `command.go` like the other commands; Makefile stays as-is
because gokit is invoked with `go run ./tools/gokit`):

```
gokit scaffold feature  --name <feature>
gokit scaffold endpoint --feature <feature> --operation <snapshot operation id>
```

`scaffold feature --name <name>`:
- Refuses a name that is not a lower-case package identifier, that already
  exists as a directory, or that duplicates an existing feature.
- Creates `internal/features/<name>/`:
  - `domain/domain.go` — empty core with the package doc.
  - `ports/ports.go` — the `Repository` interface shell.
  - `infra/repository.go` — the repository over the generated queries.
  - `app/service.go` — the service shell taking `Deps`.
  - `<name>.go` — the root: `Deps`, `Register` mounting no routes yet, and the
    exported surface the composition root consumes.
  - `<name>_test.go` — a test proving `Register` mounts without routes.
- Wires the composition root by inserting `features.Register(router, features.Deps{...})`
  between the `// gokit:feature-registrations` markers in `cmd/api/server.go`.
- Adds nothing to the contract, env.example, or the AGENTS.md map (feature
  internals are already mapped under `internal/features/`).

`scaffold endpoint --feature <name> --operation <id>`:
- Resolves the operation from `contracts/openapi.yaml`: method, path, request
  schema, and response schema. Unknown id → usage error; id not in
  `contracts/allowlist.yaml` → refuse ("already implemented or not declared").
- Generates, in the named feature (scaffolding the feature first if it is
  missing — that is the one-command path from the exit gate):
  - `app/<operation>.go` — the use case returning the response DTO.
  - `ports/ports.go` addition — the repository method the use case needs.
  - `infra/<operation>.go` — the query-backed implementation.
  - The handler plus route in the feature root, between the
    `// gokit:route-registrations` markers, using the operation id as the route
    id so the contract gate sees it as implemented.
  - A `cmd/api/contract_<feature>_<operation>_test.go` covering the happy path
    and the authentication path, so the new surface is genuinely exercised.
  - The `db/queries/common/<feature>.sql` query the repository runs, so SQL
    stays with repositories and never in handlers.
- Removes the operation from `contracts/allowlist.yaml`, which is what makes the
  coverage test pass rather than drift.

## Acceptance checks

1. `gokit scaffold feature --name reports` creates a feature whose package
   builds, and `make verify` passes untouched afterwards.
2. `gokit scaffold endpoint --feature reports --operation <allowlisted id>`
   produces a route that the contract coverage test accepts and removes the
   operation from the allowlist; `make verify` passes untouched afterwards.
3. Bad input is refused without side effects: unknown operation, an operation
   that is not allowlisted, an existing directory, and a malformed name.
4. Partial failures leave no half-written feature: the generator stages writes
   and rolls back when any step fails.
5. Golden tests cover the emitted files for one feature and one endpoint, plus
   the allowlist and marker edits, using a temp repository copy — no test writes
   into the working tree.
6. `gokit help` lists both commands and the usage text stays accurate.

## Non-goals

- No `db generate` or `contract generate` invocation from the scaffold; the
  generated queries and types are the caller's follow-up (`make generate`), and
  the scaffold documents it in its output.
- No support for scaffolding operations the snapshot does not declare.
- 6.2's `remove feature` and 6.5's CI smoke are separate slices; this plan only
  keeps the marker contract they will rely on.

## Risks and notes

- **Marker-based wiring.** The composition root and feature roots gain two marker
  pairs. The knowledge check's project-map rules do not cover them, so the plan
  records them here: they are the scaffold/remove interface and must survive
  reformatting (they are comments on their own lines).
- **OpenAPI parsing.** The scaffold reads method/path/schemas from the pinned
  snapshot rather than the generated types, because the generated types carry no
  path metadata. Parsing is limited to the paths the allowlist names, so an
  unusual construct elsewhere in the snapshot cannot break the command.
- **Response shape.** Scaffolded handlers answer with the kit's envelope
  (`{data, meta?}`) through `httpx`; the snapshot's response schema decides the
  DTO's fields, and unknown constructs (oneOf, allOf) fall back to a documented
  `TODO` the caller fills in rather than emitting something unverifiable.

## Outcome — landed 2026-10-15

- `gokit scaffold feature --name <name>`: validates the name, refuses an existing
  directory, writes the skeleton (domain, ports, infra, app, root, root test) through
  staged writes that roll back on failure, and wires the composition root between the
  `// gokit:feature-registrations` markers. The skeleton mounts no routes, so it adds
  nothing to the contract, env.example, or the AGENTS.md map.
- `gokit scaffold endpoint --feature <f> --operation <id>`: resolves the operation from
  the pinned snapshot (membership plus a method/path scan), requires it to be
  allowlisted, then writes the use case and its test, the repository read, the
  `db/queries/common/<feature>.sql` query, the route plus handler plus `handlers` struct
  in the feature root (adding the imports), a contract-test skeleton, and removes the
  operation from `contracts/allowlist.yaml` — which is what keeps the coverage test
  passing instead of drifting. Wiring rides the `// gokit:route-registrations` marker so
  6.2 can unwire it textually.
- Tests cover feature creation and wiring, the refusal set (bad name, existing
  directory, missing feature, unknown operation, unallowlisted operation), the endpoint
  emission and allowlist edit, and snapshot resolution — all against a temp fixture
  repository, so no test writes into the working tree.
- **Deviation from the plan, recorded:** the endpoint's contract test is a
  `t.Skip` skeleton naming the fixture work, not a filled-in happy/auth-path test, and
  the generated use case and repository bodies carry explicit `TODO`s for the
  snapshot-declared fields.
- Acceptance checks 1 and 2 (scaffolded output passes `make verify` untouched) are now
  proven: 6.5's `make scaffold-smoke` runs the full profile on scaffolded output and
  reports `passed — scaffolded output is gate-clean`. That smoke also drove five
  template fixes; see `completed/6.5-scaffold-smoke.md`.

Verification: `go test ./...` green (including the new `tools/gokit` tests),
`golangci-lint run` 0 issues, `make verify` full profile passed on this tree.

## Review round 1 — corrections (2026-10-15)

- **Repository interface methods are declared by hand.** The plan expected
  `scaffold endpoint` to add the method to `ports/ports.go`; the generator does not
  (it leaves `ports.Repository` as the feature's own boundary for the developer to
  shape), so the plan and `docs/guide/adding-an-endpoint.md` now say so. The infra
  stub still compiles against the empty interface until then.
- **A second endpoint appends to the feature's query file** instead of dropping its
  `db/queries/common/<feature>.sql` template, which had silently discarded the
  query the generated repository stub refers to.
- **Slug and symbol collisions**: endpoints on one resource now carry resource and
  verb (`reports.list` -> `list.go`/`handleList`, `reports.get` -> `get.go`/
  `handleGet`), covered by a two-endpoint test.
- **Idempotent registration**: imports and the `handlers` struct are added once, and
  the composition root keeps exactly one `// gokit:feature-registrations` marker,
  placed after the auth guard — the defect that had broken `make scaffold-smoke`.
