# 5.4 — Account deletion finalize + emails

- Status: active
- Owner: Core kit maintainers
- Risk: high
- Date: 2026-10-13
- Roadmap: `docs/exec-plans/roadmap.md` Phase 5
- Related ADRs: ADR-0005 (portable SQL), ADR-0006 (asynq)

## Objective

Close the deletion loop and the deferred jobs: schedule the finalize + the two deletion emails from the API, run the **de-identification transaction** in the worker with the last-admin guard and delayed-job re-scheduling, and land the two profile-image cleanup jobs that 4.4 deferred. This completes Phase 5 (exit gate: email flows end to end).

## Ground truth (read from the reference before writing code)

**Finalize (`users.finalizeAccountDeletion`, `users` queue, concurrency 2)** — `runFinalizeAccountDeletionTx`:
- missing → `skipped/user_not_found`; `DELETED` or `deletedAt` set → `skipped/already_deleted`; no schedule → `skipped/not_scheduled`; due in the future → **`not_due`** (the worker **moves the job back to delayed** at `scheduledFor`).
- Last-admin guard: an `ACTIVE` admin with ≤ 1 active admin → audit `FINALIZE_BLOCKED_LAST_ADMIN` (trace from the request or `job:<id>`; `deletionRequestedSessionId` is an invariant — throw if missing) → **`blocked_last_admin`** (re-delay **one day**).
- Otherwise, one transaction: email → **`deleted+<id>@example.invalid`** (frees the original address), `email_verified_at` null, role → `USER`, status → `DELETED`, `deleted_at` = now, the four deletion columns and suspension fields cleared; profile names nulled; **password credential, external identities, verification and reset tokens deleted**; **sessions deleted entirely** (device identifiers; refresh/push tokens cascade); then two audit rows — a status-change audit (`old → DELETED`) and `userAccountDeletionAudit` `FINALIZED`, both carrying the original session id and trace id.
- Returns `finalized` with `userId`/`deletedAt`; every skip is a successful outcome.

**Scheduling (producers, API side)**: `scheduleFinalize(userId, scheduledFor)` uses a **deterministic job id per user**, removes any existing job first (so a request/cancel cycle can reuse the id), and delays by `max(0, due − now)`; `cancelFinalize(userId)` removes that job. The request flow also enqueues the "requested" email immediately and **schedules the reminder** (offset derived from the scheduled instant — confirm the exact constant in `user-account-deletion-email.jobs.ts` while implementing); cancel removes the reminder too. Producers skip silently when the queue or email is unconfigured.

**Deletion emails** (5.2's lane): `users.sendAccountDeletionRequestedEmail` — skips `user_not_found`, `already_deleted`, `not_scheduled`; text announces the date, the cancel option, and a support line; link = the public app root. `users.sendAccountDeletionReminderEmail` — same skips plus **`too_late`** when the schedule has passed; text urges cancelling to keep the account.

**Profile-image cleanup jobs (4.4's deferred halves)**: `users.profileImage.deleteStoredFile` — skips `file_not_found` and wrong purpose, then deletes the object (best-effort) and marks the stored file deleted; `users.profileImage.expireUpload` — the 2-hour stale-upload expiry.

## Constraints

- asynq delay and cancellation: `asynq.ProcessIn(delay)` + the deterministic `asynq.TaskID(user-scoped id)`, cancelled through a new `queue.Inspector` surface (`DeleteTask`). Re-scheduling removes the pending task first, mirroring the reference's `removeJob`.
- The finalize transaction is one `InTx`; SQLite serialises writers, and the last-admin count follows the same in-transaction rule as 4.5 (pg's `FOR UPDATE` stays the recorded follow-up).
- The API schedules only when the queue is configured; `me.Deps` gains an optional producer so tests and dev boot without Redis enqueues.
- Emails render through 5.2's `platform/email`; the job payloads are the reference's `{userId, requestedAt}`.
- `deletion_requested_session_id` is required by the finalize; 4.5 always writes it from the principal.

## Impact Areas

- API / contract: no operation changes — 4.5's request/cancel gain scheduling side effects
- DB / migrations: no schema change; finalize + cleanup queries
- Auth / session: sessions and credentials are destroyed by the finalize
- Config / secrets: `USERS_ACCOUNT_DELETION_EXPIRE_DELAY_SECONDS` (the 2-hour expiry) if the cleanup slice needs it; reminder offset if configurable in the reference
- Observability: finalize logs userId/outcome; skip reasons carry through
- CI / release: worker consumes the `users` queue

## Acceptance Criteria

1. Request schedules a delayed finalize with a deterministic id and enqueues the requested email; cancel removes the delayed job and the reminder.
2. A due finalize de-identifies exactly as listed and writes both audits; a not-due job re-delays to the scheduled instant; a last-admin block audits and re-delays one day.
3. `deleteStoredFile` removes the object and marks the record deleted, skipping unknown or wrong-purpose files; `expireUpload` handles the stale case.
4. All skips are successful outcomes; the deletion emails match the reference's texts and skip sets (`too_late` included).
5. `make verify` green; generated code committed.

## Outcome — landed 2026-10-15

Implemented in one slice:

- `queue.Scheduler` (platform): deterministic delayed jobs — remove-then-enqueue so
  request/cancel cycles reuse the id, `delay = max(0, due - now)`, cancel treats a
  missing task as success.
- `users.finalizeAccountDeletion` on the new `users` queue: skips (missing, deleted,
  not scheduled as successes), re-arms itself at the stored instant when not due, audits
  `FINALIZE_BLOCKED_LAST_ADMIN` and re-checks after a day for a lone active admin, and
  otherwise de-identifies in one transaction — scrubbed `deleted+<id>@example.invalid`
  address, cleared verification/role/status/suspension/deletion columns, nulled profile
  names, deleted credentials, external identities, both token tables, and all sessions —
  writing the `FINALIZED` audit with the requesting session and trace.
- Producers in `me/app` arm `finalize:<userId>` at the stored due instant plus the
  requested email now and the reminder `ReminderLead` (72 h, our value — the reference's
  offset is unresolved) before the deadline; cancel removes the finalize and reminder.
  Emails are best effort; the finalize arm propagates its failure.
- Deletion emails on the `emails` queue with the reference's skip set (missing, deleted,
  not scheduled) plus `too_late` on the reminder.
- Stored-file cleanup: `users.profileImage.deleteStoredFile` (skip unknown, wrong
  purpose, already deleted; best-effort object delete then mark deleted) and
  `users.profileImage.expireUpload` (skip unknown and not-uploading; expire then drop the
  object), the latter armed at upload-plan time with
  `USERS_PROFILE_IMAGE_UPLOAD_EXPIRE_DELAY_SECONDS` (7200 default) — closing 4.4's
  deferred durable cleanup.
- The last-admin guard counts inside the finalize transaction itself (a suspended admin
  is not counted as active), so concurrent finalizes cannot both pass it; the worker
  consumes the `users` queue, and the API closes its scheduler on shutdown. A retry of
  the request re-arms the finalize job from the stored schedule, so a transient
  scheduling failure cannot strand the account.
- Schema 0007 on both engines: `users.deleted_at` and the audit action CHECK widened to
  admit `FINALIZED` / `FINALIZE_BLOCKED_LAST_ADMIN` (both engines rebuild the table so the
  schema inventory stays parity-clean).
- Worker registration with the users/emails lanes; skips log at warn, sends and finalizes
  at info with the provider email id.
- Recorded divergences: no status-change audit table yet (arrives with the Phase 8 admin
  slice; only account-deletion audits are written), and the cleanup handlers register only
  when object storage is configured.
