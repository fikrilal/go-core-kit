# 6.3 — `doctor` + completion of `db generate`

## Objective

Close the CLI's operational gaps: the prerequisite inspector and the database
generator should both be complete enough to trust in CI and on a fresh clone.

## What was already there

`gokit doctor` covers the checks this task was tracking: repository files
(`go.mod`, `Makefile`, `sqlc.yaml`, `AGENTS.md`, `docs/README.md`), the installed
Go toolchain against `go.mod`'s directive, the Makefile's tool pins
(golangci-lint, sqlc, oapi-codegen, vacuum) against the installed versions, and
whether the tree is a git work tree. Those checks are now documented for users in
`docs/guide/config.md` instead of living only in the command.

`gokit db generate` already ran sqlc, packaged both engines into
`internal/db/gen` with build tags, and removed stale engine files.

## The completion

`db generate` wrote its sqlc workspace to `.gen/` and left it behind after every
run. The scratch directory is now removed on both paths — success and failure —
so a generation error cannot leave intermediates that look like part of the tree.
`.gen/` stays in `.gitignore` as a belt-and-braces measure.

## Acceptance checks

1. `make generate` leaves no `.gen/` directory behind.
2. A failing sqlc run also leaves none.
3. `make verify` stays green (the drift gate compares the regenerated artifacts).

## Outcome — landed 2026-10-15

The scratch cleanup is in place, and `make verify` full profile passed after
regeneration. No further gaps were identified against ADR-0010's command list:
every command it names exists, and each one is exercised by `make verify` or by
the scaffold smoke.

## Notes

- Doctor deliberately does not dial Redis or open the database: it answers "can I
  build and verify here", not "is my deployment reachable". Runtime readiness is
  the worker's `/ready` probe and the API's own startup checks.
