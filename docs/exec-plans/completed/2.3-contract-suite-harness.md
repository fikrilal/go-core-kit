# 2.3 — Contract suite harness

- Status: completed
- Owner: Core kit maintainers
- Risk: medium
- Date: 2026-10-10
- Roadmap: `docs/exec-plans/roadmap.md` task 2.3
- Related ADRs: ADR-0002 (parity), ADR-0002 (headers/status assertions)

## Objective

Build the live-response contract harness: test-only helpers (`kin-openapi`) that validate real responses against the pinned snapshot and assert the non-schema parity behaviors clients rely on — `X-Request-Id` echo, problem details shape, and `x-error-codes` membership. Baseline it against the implemented `health.get` / `ready.get` operations.

## Constraints

- Harness lives in `internal/platform/contracttest` (test-support package; never imported by production code; `kin-openapi` v0.149.0 is a test-only dependency).
- Snapshot path is overridable via `CONTRACT_SNAPSHOT_PATH` (needed by 2.5's gate-honesty injection); default is `contracts/backend.openapi.yaml`.
- Tests boot the real composition (`newServer`) with a temp SQLite database and miniredis — no mocks of the platform chain.
- Validation is test-time only; zero runtime cost in the API binary.
- Assertions match what clients observe: status, `Content-Type`, body vs snapshot schema, header echo, RFC7807 fields (`code`, `traceId`).

## Impact Areas

- API / contract: yes (the parity proof mechanism)
- DB / migrations: no (temp SQLite for boots)
- Auth / session: no
- Queue / jobs: no
- Config / secrets: no
- Observability: no (asserts `traceId` presence, not logging)
- CI / release: yes (runs inside `go test ./...`, hence `make verify`)

## Acceptance Criteria

1. `contracttest.Suite` loads and validates the pinned snapshot; failures explain the operation, status, and schema mismatch.
2. Baseline tests in `cmd/api` boot the live server and validate `/health` and `/ready` responses against the snapshot, including `X-Request-Id` echo and the 503 problem path when Redis is down.
3. `AssertProblem` checks RFC7807 shape, `code` equality, `traceId` presence, and membership of the code in the operation's `x-error-codes`.
4. The harness is documented in `docs/standards/testing-strategy.md` (lands with this task) and referenced from the roadmap's contract section.
5. `make verify` green with the baseline tests included.

## Decision Log

- 2026-10-10: Test-time validation only — parity does not cost runtime bytes or CPU (proposal: "validation in tests only").
- 2026-10-10: Tests boot the real composition instead of a reduced router — the middleware chain is part of the observed contract.
- 2026-10-10: `x-error-codes` membership is asserted per operation because clients branch on error codes (contract, not copy).

## Verification

```bash
go test ./cmd/api/... -run Contract -count=1 -v
make verify
```

Outcome: `TestContractProbes` boots the real composition (temp SQLite + miniredis) and proves — `/health` and `/ready` validate against the pinned snapshot (`status` schema); a client-provided `X-Request-Id` is echoed byte-identically; `/ready` degrades to a 503 `unavailable` body with the failing check named; unknown paths return an RFC7807 `NOT_FOUND` problem whose `traceId` equals the echoed request id; `ready.get` declares `INTERNAL` in `x-error-codes`. Harness API returns a value type (`contracttest.Response`) so no response bodies leak — bodyclose-clean. `make verify` green.

## Completion Notes

`kin-openapi v0.149.0` is a test-only dependency; `CONTRACT_SNAPSHOT_PATH` overrides the snapshot (used by 2.5). The suite resolves the repo root by walking up to `go.mod`, so tests can live in any package. Two refinements during the task: `ResponseValidationInput` requires the original request (a nil `Request` panics inside kin-openapi) and the `Do` helper returns a value type rather than `*http.Response` so response bodies cannot leak. `docs/standards/testing-strategy.md` is normative; the standards index marks it in place.
