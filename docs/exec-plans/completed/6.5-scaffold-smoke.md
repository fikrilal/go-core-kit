# 6.5 — Scaffold smoke

## Objective

Prove that scaffolded output passes the full gate untouched, which is what
turns 6.1's templates from a claim into a checked property: a fresh clone can
scaffold a working endpoint in one command and stay green.

## Design

`tools/gokit/scaffold-smoke.sh`, run through `make scaffold-smoke` and wired into
CI after `make verify`:

1. copy the working tree to a temporary directory (the scaffold tool itself is
   usually uncommitted, so a clone would miss it),
2. commit the baseline, so the drift gate has a clean reference,
3. `gokit scaffold feature --name merchantonboarding`,
4. `gokit scaffold endpoint --feature merchantonboarding --operation merchantOnboarding.referenceData.get`
   — an allowlisted, not-yet-ported operation used as a throwaway stand-in: the
   smoke cares that the templates are gate-clean, not about feature placement,
5. `make generate` for the derived artifacts, then commit the result,
6. `make verify` — the full profile, in the copy, which must pass untouched.

The copy keeps the real repository clean: nothing the smoke does touches the
working tree, and the temporary directory is removed on exit. The smoke is not
part of `go test ./...`, because `make verify` runs the suite and the smoke runs
`make verify` — nesting them would recurse.

## Acceptance checks

1. `make scaffold-smoke` passes on a tree whose scaffold templates are correct,
   and fails loudly on the first gate the scaffolded output breaks.
2. The gate steps the smoke reports are the same profile CI runs.
3. A failure names the step (`fmt-check`, `vet`, `lint`, `test`, `drift`) and
   leaves no artifacts in the caller's working tree.

## Outcome — landed 2026-10-15

`make scaffold-smoke` and the CI step are in place, and the smoke surfaced and
closed five real template defects, each of which would have made scaffolded
output fail the gate:

- the route line was inserted before the wiring it uses, and the `handlers`
  struct carried an unused guard field;
- generated files were not gofmt-clean (`gofmt` now runs on every generated Go
  file, so template spacing cannot leak into the tree) and the inserted
  `net/http` import landed in the wrong group;
- the use case was emitted with an unexported name, the handler called
  `httpx.WriteJSON` (the kit's helper is `httpx.Data`), and the feature-root test
  built `httpx.NewRouter()` without its logger;
- the feature-root test asserted the router's unmounted-path status, which is
  not this kit's property to pin, and called `Register` without the database the
  composition root always supplies;
- the composition-root marker sat above the auth guard, so the inserted
  registration referenced a variable that did not exist yet.

Final state: `make scaffold-smoke` reports `passed — scaffolded output is
gate-clean`, i.e. `make verify` full profile passes on the scaffolded tree,
which closes 6.1's recorded deviation (acceptance checks 1 and 2 there).

## Notes

- The smoke also pins the marker contract: `// gokit:feature-registrations` in
  the composition root must stay after the auth guard, or scaffolded features
  will not compile there.
- `merchantOnboarding.referenceData.get` is consumed by the smoke copy only; the
  real allowlist still lists it.
