# 3.7 — Password reset request + confirm

## Objective

Implement the two remaining Phase 3 operations and close Phase 5's exit gate with
them: `auth.password.reset.request` and `auth.password.reset.confirm`. After 3.6,
the worker half already exists — 5.2's `auth.sendPasswordResetEmail` mints the
token (SHA-256/base64url hash, 30-minute TTL) and sends it on the `emails` lane.

## Contract (from the pinned snapshot)

**`POST /v1/auth/password/reset/request`** — public, body
`PasswordResetRequestDto` (`email` required), `204`. Codes: `VALIDATION_FAILED`,
`RATE_LIMITED`, `INTERNAL`. The description calls it rate limited, and there is no
`UNAUTHORIZED`: the route is anonymous by design.

**`POST /v1/auth/password/reset/confirm`** — public, body
`PasswordResetConfirmRequestDto` (`token`, plus the new password), `204`. Codes:
`VALIDATION_FAILED`, `AUTH_PASSWORD_RESET_TOKEN_INVALID`,
`AUTH_PASSWORD_RESET_TOKEN_EXPIRED`, `INTERNAL`.

## Design

**Request — no oracle, rate limited, enqueue only.** The service takes the email,
normalizes it, and reports only whether a reset may be sent: an unknown or deleted
account answers success without enqueuing, and the route enqueues
`auth.sendPasswordResetEmail` only when told to — the same `(shouldEnqueue, err)`
shape 3.6 landed after the review caught the alternative. The per-email limit runs
before the account lookup, under its own Redis scope (`auth:password_reset`) and
its own message, so a request attempt is always counted and the answer never
depends on whether the address exists. The provider gate answers
`AUTH_EMAIL_NOT_CONFIGURED` when no sender is configured, as the resend route does.

**Confirm — one transaction.** New queries:
`GetPasswordResetTokenByHash` (joined to the account status) and
`ConsumePasswordResetTokenAndSetPassword`, which inside one `InTx`:
1. marks the token used with a compare-and-set (`used_at IS NULL`) and stops if it
   lost the race;
2. writes the new credential hash (`UpdatePasswordCredentialHash`, falling back to
   the create query for an account that has no credential yet — an OIDC-only
   account may set a password this way);
3. deletes the account's sessions and its refresh tokens, so every existing device
   is signed out by the reset.

The password itself is validated at the DTO (required) and by the service's
existing length policy (`passwordTooShortError`), and hashed with the platform
password hasher the register and change-password paths use. Unknown hash →
`AUTH_PASSWORD_RESET_TOKEN_INVALID`; used, expired, or race-lost →
`AUTH_PASSWORD_RESET_TOKEN_EXPIRED`; a deleted account →
`AUTH_PASSWORD_RESET_TOKEN_INVALID`, never a different answer.

**New typed codes:** `AUTH_PASSWORD_RESET_TOKEN_INVALID` and
`AUTH_PASSWORD_RESET_TOKEN_EXPIRED` in `httpx`, with named problems in
`app/problems.go` (`401`, matching the verification family, since the snapshot
declares codes and not statuses).

**Config:** `AUTH_PASSWORD_RESET_REQUEST_MAX_ATTEMPTS|WINDOW_SECONDS|BLOCK_SECONDS`,
documented in `env.example` and validated beside the login and resend knobs.

## Acceptance checks

1. Request: unknown email → 204 and nothing enqueued; known and active → 204 with a
   job on the `emails` lane carrying the request meta; over the limit → `429
   RATE_LIMITED` with `Retry-After`; unconfigured sender → `501`; malformed body →
   `VALIDATION_FAILED`.
2. Confirm: a token minted by the worker job's query verifies end to end — the
   credential hash changes, sessions and refresh tokens are gone, and the token
   cannot be replayed (its own code), expire silently, or be used for a deleted
   account.
3. Both operations leave the allowlist (**10 → 8**), the coverage test stays green,
   and `make verify` passes on the committed tree.
4. Unit tests cover each problem code and the skip path; a `cmd/api` contract test
   drives both routes including the live 204 (a queued fixture, as 3.6 added).

## Notes and risks

- The hash must match 5.2's minting helper exactly
  (`domain.HashPasswordResetToken`); the first integration test asserts a
  worker-minted token confirms, which is the check that pins that agreement.
- Reusing the generated `DeleteUserSessions` (written for the account-deletion
  finalize) keeps one definition of "sign the account out"; the plan records that
  the query is shared across features through `internal/db/gen` rather than
  duplicated.
- Resetting a password for an account that has no credential creates one; the
  alternative (the `AUTH_PASSWORD_NOT_SET` answer the change-password route uses)
  would leave an OIDC-only account unable to recover, and the reset code list has
  no such code.

## Progress — increment 1: the confirm use case (2026-10-15)

- `GetPasswordResetTokenByHash` and `MarkPasswordResetTokenUsed` in
  `db/queries/common/auth.sql`, both generated.
- `ConsumePasswordResetTokenAndSetPassword` on the repository: one `InTx` that
  compare-and-set marks the token used, writes the credential (creating one for an
  account that has none), and deletes the account's sessions — which cascade to
  their refresh tokens, so no extra delete was needed.
- `Service.ConfirmPasswordReset`: length policy first, then the same problem codes
  as the verification family (invalid for unknown or unverifiable, expired for
  used, expired, or race-lost), hashing with the platform hasher the register path
  uses. Unit tests cover the happy path, the length policy, and every code.
- The token lookup is now **one** repository method, `TokenByHash(kind, hash)`
  (`ports.TokenKind`), rather than two near-identical loaders: the reset work made
  the duplication explicit, and the linter's `dupl` rule was the signal that a kind
  discriminator belongs in the port.

Remaining: the request operation (route, per-email limiter under
`auth:password_reset`, enqueue on the emails lane), the confirm route and its
contract test, then the allowlist drop to 8 and closure.

## Outcome — landed 2026-10-15

Both operations are implemented and covered, and the allowlist closed at **8**.

- **`auth.password.reset.confirm`** (public): `ConsumePasswordResetTokenAndSetPassword`
  runs in one `InTx` — compare-and-set mark-used, credential write (creating one
  for an account that has none, so an OIDC-only account can recover), and session
  deletion that cascades to refresh tokens. The service applies the length policy
  first and answers the invalid code for unknown or unverifiable tokens and the
  expired code for used, expired, or race-lost ones. Its contract test proves the
  credential actually changed by **logging in with the new password**, and covers
  replay, unknown token, and DTO validation.
- **`auth.password.reset.request`** (public): the provider gate, then the
  per-address limiter under its own scope (`auth:password_reset`) and message, then
  the account lookup. The service returns the account to mail or an empty id, so an
  unknown or deleted address answers 204 with nothing enqueued; the route enqueues
  `auth.sendPasswordResetEmail` only for a real account. Unit tests cover every
  gate; the contract test covers the unconfigured gate, validation, the no-oracle
  204, and the declared `RATE_LIMITED`.
- **One lookup for both token tables**: `TokenByHash(kind, hash)` with
  `ports.TokenKind` replaced two near-identical loaders — the reset work exposed the
  duplication and the linter's `dupl` rule pointed at the fix, which is a kind
  discriminator in the port rather than a suppressed warning.

**A bug the contract test caught:** `app.Deps.RequestLimiter` was declared and
consumed but never assigned in `Register`, so the first request panicked into a
500 on the queued fixture. The unconfigured fixture had hidden it, because the
provider gate returns before the limiter runs. With the limiter wired, the live
path answers 204 and the declared `RATE_LIMITED` as designed.

Verification: `go test ./...` green, `golangci-lint run` 0 issues, `make verify`
green except the uncommitted-drift step.
