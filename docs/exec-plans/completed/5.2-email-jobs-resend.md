# 5.2 — Email jobs + Resend adapter

- Status: completed
- Owner: Core kit maintainers
- Risk: medium
- Date: 2026-10-13
- Roadmap: `docs/exec-plans/roadmap.md` Phase 5
- Related ADRs: ADR-0006 (asynq), ADR-0007 (config)

## Objective

Land the email lane: a Resend adapter and email queue in `internal/platform/email`, the two auth email jobs (`auth.sendVerificationEmail`, `auth.sendPasswordResetEmail`) minting tokens in the worker, and the config/templates they need. Unblocks 3.6/3.7, whose API side only verifies presented tokens. Allowlist untouched.

## Ground truth (read from the reference before writing code)

- Queue: dedicated `emails` queue (`queueName('emails')`); job names `auth.sendVerificationEmail` and `auth.sendPasswordResetEmail` (dot-separated lowerCamel). Producers enqueue `{userId, requestedAt}` and **skip enqueueing entirely** when the queue or email service is disabled, or when `PUBLIC_APP_URL` is missing (reset).
- Adapter (`libs/platform/email/email.service.ts`): enabled only when `RESEND_API_KEY` **and** `EMAIL_FROM` are non-empty; optional `EMAIL_REPLY_TO`; input `to/subject/text?/html?/from?/replyTo?/tags?/headers?`; result `{id}`; provider failures wrap as a send error naming the provider.
- **Worker handlers mint the tokens** (`apps/worker/src/jobs/emails.handlers.ts`):
  - Verification: TTL from `AUTH_EMAIL_VERIFICATION_TOKEN_TTL_SECONDS`; load user → missing ⇒ `skipped/user_not_found`, `DELETED` ⇒ `skipped/already_deleted`, already verified ⇒ `skipped/already_verified` (all **successful** job outcomes); otherwise insert `email_verification_tokens{userId, tokenHash, expiresAt}` (token generated + hashed), build the link from `PUBLIC_APP_URL` (absent ⇒ token-only text, still sent), send subject "Verify your email" with text listing the token and link plus the expiry, return `{ok, userId, outcome:"sent", emailId, tokenExpiresAt}`.
  - Password reset: same shape with `AUTH_PASSWORD_RESET_TOKEN_TTL_SECONDS` and `password_reset_tokens`; **missing `PUBLIC_APP_URL` throws** (the link is required for reset), so the job retries.
- Token tables (Prisma): `email_verification_tokens` / `password_reset_tokens` with unique `token_hash`, `expires_at`, `used_at`, `revoked_at`, `created_at`, `updated_at`, and indexes on user/expiry/revoked/used. The API side (3.6/3.7) consumes them by hash, so they land here.
- Templates live beside the worker handlers in the reference: verify URL builder, brand name from `PUBLIC_APP_URL`, and an HTML renderer per email.
- Config: `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_REPLY_TO` (optional), `PUBLIC_APP_URL`, `AUTH_EMAIL_VERIFICATION_TOKEN_TTL_SECONDS`, `AUTH_PASSWORD_RESET_TOKEN_TTL_SECONDS`.

## Constraints

- Resend via a small **stdlib HTTP client** (`POST https://api.resend.com/emails`, bearer key) — no SDK dependency; a `Sender` port keeps the worker tests offline with a recording double.
- Tokens: 32 random bytes, base64url, stored **SHA-256 hashed** (mirroring the refresh-token pattern already in the auth feature).
- The worker composes feature job handlers the same way the API composes HTTP ones: `auth.RegisterJobs(mux, deps)` — the feature owns its SQL and policy; `cmd/worker` stays a composition root.
- Skips are **successful** job outcomes (no retry), and each skip logs at warn; the reset job's missing-URL failure is the only throw.
- Email HTML/text renderers live in `internal/platform/email` (three features' emails share one shell), taking brand, link, token, and expiry.
- Migration 0006 adds the two token tables (both engines) + sqlc overrides for their timestamps; the `emails` queue joins the worker's queue map with equal priority.

## Impact Areas

- API / contract: no operations yet (3.6/3.7 add them); allowlist untouched
- DB / migrations: yes — migration 0006, two token tables
- Auth / session: token minting moves to the worker; the API only consumes
- Config / secrets: Resend key, from/reply-to, `PUBLIC_APP_URL`, two TTLs (+ `env.example`)
- Observability: handler logs carry userId, outcome, and the provider email id
- CI / release: worker consumes `emails`; no new binaries

## Acceptance Criteria

1. `platform/email` sends through a recording double and a Resend-shaped HTTP stub, reports the provider id, fails with a named provider error, and stays disabled without key/from.
2. `auth.sendVerificationEmail`: mints a token row, sends the link + token with the TTL, and returns `sent`; the three skip paths return success without inserting or sending.
3. `auth.sendPasswordResetEmail`: same, and throws when `PUBLIC_APP_URL` is unset (so asynq retries).
4. The worker registers both handlers on the `emails` queue; an enqueue→consume round trip through the platform queue reaches the handler with `request_id`/`trace_id` intact.
5. `make verify` green; generated code committed.

Outcome: the email lane is live. `internal/platform/email` ships a stdlib Resend client (enabled by key + sender, optional reply-to, provider errors named), the shared branded text/HTML templates with the reference's link builders (`/verify-email?token=`, `/reset-password?token=`) and host-derived brand, and the `emails` queue name. The two auth jobs mint tokens in the worker — `auth.sendVerificationEmail` and `auth.sendPasswordResetEmail` — with the reference's skip semantics (missing/deleted/already-verified succeed without a write or a send), 24 h / 30 min TTLs, and the reset job failing when `PUBLIC_APP_URL` is unset so the retry policy applies. `cmd/worker` registers both handlers on the `emails` queue when Resend is configured, logging the propagated request/trace ids. Migration 0006 adds `email_verification_tokens` and `password_reset_tokens` on both engines, and `queue.Bind` adapts typed handlers to the queue.

Verification: email tests cover the disabled client, the Resend payload and bearer auth against an HTTP stub, provider error wrapping with status and detail, message validation, and the template URLs/text/HTML plus the empty-URL and invalid-brand fallbacks. Auth job tests cover the sent path (token stored with the right TTL, link in the message), all three verification skips, the reset path, the reset no-URL failure with the skip ordering (a missing account still skips), and provider failure propagation. The worker test asserts no handlers without Resend configuration and both registrations with it; the migration down/up test now walks to the 0001 skeleton through five levels and back. `golangci-lint run` 0 issues; both build lanes pass; `make verify` full profile passed on a scratch copy with the regenerated artifacts committed (the live tree's `drift` is red by design until commit).

## Completion Notes

Deviations and discoveries: `queue.Bind` was added so the worker composes typed handlers without the feature importing asynq; the feature exposes `auth.NewEmailJobs` from its root, keeping `cmd/worker` free of internal subpackages (the 4.4 review finding). The token helpers were extracted into private `newOpaqueToken`/`hashOpaqueToken` shared by refresh, verification, and reset tokens. The reset handler checks `PUBLIC_APP_URL` **after** the account skips, mirroring the reference exactly, so a deleted or missing account stays a successful skip even with no URL configured. The reference's HTML design is not mirrored (only its content); the text body, subjects, link paths, and TTLs are.
