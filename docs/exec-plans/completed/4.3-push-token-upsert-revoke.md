# 4.3 — Push token upsert/revoke

- Status: completed
- Owner: Core kit maintainers
- Risk: medium
- Date: 2026-10-12
- Roadmap: `docs/exec-plans/roadmap.md` Phase 4
- Related ADRs: ADR-0001 (feature tiers), ADR-0007 (config)

## Objective

`users.me.pushToken.upsert` (`PUT /v1/me/push-token`) and `users.me.pushToken.revoke` (`DELETE /v1/me/push-token`) in `internal/features/me`, at parity with backend-core-kit `MePushTokenController` / `AuthPushTokensService`, against the client behaviour mobile-core-kit implements. Allowlist 20 → 18.

## Ground truth (read from both references before writing code)

**backend-core-kit**

- Controller: **501** `AUTH_PUSH_NOT_CONFIGURED` ("Push provider is not configured") when `push.isEnabled()` is false — before any store work. Body `{platform, token}`; platform is trimmed + **uppercased** then must be `ANDROID|IOS|WEB`; token is trimmed, length 1..2048. **No `Idempotency-Key` parameter** on either op.
- Service: `requireExistingNonDeletedUser` first (401) on both ops. Upsert: repo may report a session problem → 401 `UNAUTHORIZED`. Revoke: always succeeds when the user exists.
- Repository upsert, one transaction: (1) validate + lock the caller's session `id, userId, revokedAt IS NULL, expiresAt > now` by bumping `push_token_updated_at`; 0 rows → `session_not_found` (401). (2) clear the token from **any other session holding it** (account switching on one install) and stamp `push_token_revoked_at`. (3) set the caller's `push_platform`, `push_token`, `push_token_updated_at`, `push_token_revoked_at = NULL`. Unique-violation retries exist for pg.
- Repository revoke: single `updateMany where id, userId` clearing platform/token and stamping updated/revoked times. **No session-state gate** (works for a revoked or expired session; already-cleared is a no-op) — this is what makes sign-out revoke best-effort.
- Snapshot: upsert codes `VALIDATION_FAILED, UNAUTHORIZED, AUTH_PUSH_NOT_CONFIGURED, INTERNAL`; revoke codes `UNAUTHORIZED, INTERNAL`.

**mobile-core-kit (the client this serves)**

- `MePushTokenRemoteDataSource` calls `PUT`/`DELETE` on `UserEndpoint.mePushToken` with both `Idempotency-Key` headers and a body of `{platform: apiValue, token}` where apiValue ∈ `ANDROID|IOS|WEB` (`push_platform.dart`); desktop maps to null ("push not supported").
- `PushTokenSyncService` syncs on session change and on FCM token rotation, dedupes via a local store, applies a **24-hour cooldown on `AUTH_PUSH_NOT_CONFIGURED`** (so the 501 is expected client behaviour), stops retrying on `UNAUTHORIZED` for the session key, and retries other failures after 15s.
- `SessionPushTokenRevokerImpl` calls revoke on sign-out and must never throw (best-effort) — so revoke must not require a live session.

## Constraints

- No FCM in this slice (that is 5.3): the "provider configured" gate mirrors the reference with a config flag `PUSH_ENABLED` (default false) surfaced as `me.Deps.PushEnabled` → 501 until credentials exist. Recorded: 5.3 replaces the flag with credential-derived detection.
- Platform normalization (trim + upper) and the 1..2048 bound live in `app` policy, like the profile patch validation; decode keeps `required`.
- Upsert is idempotent by replacement (no `Idempotency-Key` on the route, matching the snapshot). The mobile client's header is ignored by design.
- Token ownership is exclusive: the clear-other-session step runs **only after** the caller's session is validated, so a revoked session cannot clear another session's token (reference comment; keep it).
- Reuse the schema as-is: `push_platform` CHECK already constrains `ANDROID|IOS|WEB`; `push_token` is UNIQUE.

## Acceptance Criteria

1. Upsert with push disabled → 501 `AUTH_PUSH_NOT_CONFIGURED`; with it enabled → 204 and the session row carries platform/token; a repeat is 204 with the same single row state.
2. A token registered by another session of the same user is cleared from that session (platform/token NULL, `push_token_revoked_at` set) and attached to the caller.
3. Registering from a revoked or expired session → 401 `UNAUTHORIZED`, and the other session's token is untouched.
4. Validation: missing fields → 400; `platform` is trimmed/uppercased (`ios` → `IOS`); unknown platform → 400 field `platform`; token of 1..2048 stays, 2049 → 400 field `token`; whitespace-only token → 400.
5. Revoke → 204, clears the caller's row, repeats are 204, and it works while push is disabled and for an already-revoked session.
6. Deleted users → 401 on both ops; missing token → 401 on both ops.
7. `make verify` green; generated code committed.

## Completion Notes

Order of checks mirrors the reference's layering exactly: the Nest pipe validates the body first (400), the controller's provider gate runs second (501), the service's account check third (401), and the session state last inside the repository (401) — so a disabled deployment still reports invalid bodies as 400 and only a valid, configured call reaches the account check. The mobile `PushTokenSyncService` confirms this shape from the client side: it treats `AUTH_PUSH_NOT_CONFIGURED` as a 24-hour cooldown, stops retrying on `UNAUTHORIZED`, and de-dupes with a local store.

`PUSH_ENABLED` is a deliberate placeholder for the reference's credential-derived `isEnabled()`; 5.3 replaces it with FCM credential detection and adds the send path. The nullable writes reuse the `NULLIF(..., '')` house pattern, so tokens/platforms cannot be persisted empty even though the schema allows NULL. One lint friction worth remembering: gosec flags push-token literals in tests, so the fixture carries a scoped `//nolint:gosec` on the call line.
