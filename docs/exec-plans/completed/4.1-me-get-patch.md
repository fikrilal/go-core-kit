# 4.1 — `/v1/me` GET/PATCH

- Status: completed
- Owner: Core kit maintainers
- Risk: medium
- Date: 2026-10-12
- Roadmap: `docs/exec-plans/roadmap.md` Phase 4
- Related ADRs: ADR-0001 (feature tiers), ADR-0003 (HTTP behavior), ADR-0005 (portable SQL), ADR-0007 (config)

## Objective

Land the first Phase 4 slice: `internal/features/me` serving `GET /v1/me` (`users.me.get`) and `PATCH /v1/me` (`users.me.patch`) at parity with backend-core-kit `MeController` / `MeService`. New feature tier copied from auth: `domain` / `ports` / `app` / `infra` + root wiring. Allowlist 24 → 22.

## Ground truth (read from the reference before writing code)

- `getMe(userId)`: load the user with profile + auth methods + deletion fields; missing or `DELETED` → `UserNotFoundError` → **401 `UNAUTHORIZED`** (UsersErrorFilter maps it to an unusable-token 401, not a 404). View: `roles: [role]`, `authMethods`, profile (all-null default when no row), `accountDeletion` null unless requested.
- `updateMeProfile(userId, patch)`: one transaction — `updateMany({id, status != DELETED}, {updatedAt: now})` (row lock + `updated_at` bump; 0 rows → 401), `userProfile.upsert({userId, ...provided})` (creates the row when missing), re-read, return the view.
- Patch semantics: **omitted = unchanged, explicit `null` = clear, string = trim then non-empty and ≤ 100** (class-validator `MAX_PROFILE_FIELD_LENGTH = 100`); at least one of `displayName`/`givenName`/`familyName` must be defined (`AtLeastOneDefined`, message "At least one profile field must be provided"); `profileImageFileId` is read-only here.
- Snapshot: `GET /v1/me` → 200 `MeEnvelopeDto`, codes `UNAUTHORIZED, INTERNAL`; `PATCH /v1/me` → 200 `MeEnvelopeDto`, optional `Idempotency-Key`, codes `VALIDATION_FAILED, UNAUTHORIZED, IDEMPOTENCY_IN_PROGRESS, CONFLICT, INTERNAL`. Both `security: access-token`.
- `MeDto.accountDeletion` and `MeProfileDto.profileImageFileId` are optional/nullable: 4.1 answers without them; 4.4/4.5 wire them.

## Constraints

- **Absent vs null vs value** cannot ride on Go pointers (both decode to nil). Features may not import `encoding/json` (depguard), so the tri-state type lives in `internal/platform/httpx` — one call site, justified by the import ban, not by speculation.
- **One guard, one construction**: `auth.Register` now returns its `*platformauth.Guard`; `cmd/api` passes it to `me.Deps`. No second keyring parse, no implicit registration order.
- Patch validation is feature policy (like `checkPasswordPolicy`): all issues collected, deterministic field order, `VALIDATION_FAILED`.
- Length is rune count (kit precedent, see the auth note); the reference counts UTF-16 units. Divergence only for astral-character names — recorded, not chased.
- The profile merge happens in the repository transaction (portable SQL, no `CASE`-in-upsert): touch → read profile → merge in Go → upsert → re-read.
- Reuse the shared `GetMeView` / `GetAuthMethods` queries; no cross-feature import of auth types.

## Acceptance Criteria

1. `GET /v1/me` returns the envelope for the authenticated user: id, email, emailVerified, `roles`, `authMethods` (PASSWORD for a password account), profile with null fields when no row exists; 401 without a valid token.
2. `PATCH /v1/me` applies a partial patch: omitted fields unchanged, `null` clears (SQL NULL), strings trimmed and validated (`min 1`, `max 100` runes); creates the profile row when missing; bumps `users.updated_at`.
3. Invalid patches are 400 `VALIDATION_FAILED` with `errors[]`: `profile` "At least one profile field must be provided" when nothing is defined; per-field issues for empty or over-long values.
4. Missing or deleted users are 401 `UNAUTHORIZED` on both routes.
5. `PATCH` honors `Idempotency-Key` (replay returns the cached 200 + `Idempotency-Replayed: true`); unauthorized requests never prime the store.
6. `make verify` green; generated code committed.

## Completion Notes

Two reference details the tests now lock: a **missing** `profile` is a decode-level `required` issue ("profile is required"), while an **empty** `profile` object is the feature-level "At least one profile field must be provided" — the reference splits these the same way (`IsDefined` vs `AtLeastOneDefined`). And the deleted-user rule lives in two places on purpose: `TouchUser` refuses `DELETED` rows (0 rows → 401) and `meView` re-checks the status, so both the read and the write path mask a deleted account.

The tri-state decode (`httpx.OptionalString`) exists because Go pointers cannot tell absent from null and features cannot import `encoding/json`; the me handler converts it into the framework-free `domain.ProfilePatch` immediately. The nullable write reuses the house `NULLIF(..., '')` pattern, so the feature never names `sql.NullString`. `orderAuthMethods` and `nullableString` are copied from auth on purpose (features own their types and wire mapping; a third consumer is the trigger to revisit `internal/shared`).
