# 5.1 — Worker bootstrap

- Status: completed
- Owner: Core kit maintainers
- Risk: medium
- Date: 2026-10-13
- Roadmap: `docs/exec-plans/roadmap.md` Phase 5
- Related ADRs: ADR-0006 (Redis roles: asynq queue), ADR-0001 (tiers)

## Objective

Stand up the second process: `cmd/worker` plus `internal/platform/queue`. The API keeps enqueueing through the platform client; the worker consumes, owns retries/backoff, and exposes `/health` + `/ready`. No job types yet — 5.2/5.3/5.4 add them; this slice proves the wiring end to end.

## Ground truth (read from the reference before writing code)

- Kit decisions already recorded: `internal/platform/queue` owns "asynq wiring, job names, OTel propagation" (`docs/core/project-architecture.md`); `cmd/worker` "consumes jobs, owns retries/backoff, and exposes /health + /ready"; ADR-0006 pins **asynq** for email, push, and deletion jobs.
- Reference queue policy (`libs/platform/queue`): **5 attempts**, **exponential backoff, base 1 s, 0.2 jitter**; retention for completed/failed jobs; job names are dot-separated lowerCamel (`user.sendVerificationEmail` style), queue names are lowercase with hyphens; the producer stamps `__meta.otel.traceparent` into the payload when a span is active, and the worker reads it back.
- The reference's Redis connection for queues comes from `REDIS_URL` (same as the API).
- The API process owns migrations (`cmd/api` migrates before listen); the worker starts after the schema is current.

## Constraints

- New dependency: `github.com/hibiken/asynq` (ADR-0006 sanctioned). It must coexist with the pinned `github.com/redis/go-redis/v9` used by `internal/platform/redis`; a version bump of go-redis is acceptable if asynq requires it, and the platform redis client keeps its own surface.
- Queue payloads are JSON objects; job metadata rides **inside** the payload under `__meta` (request id, trace id) since there is no OTel package yet — when OTel lands, `traceparent` joins the same struct. The worker logger binds `request_id`/`trace_id` from the meta.
- Defaults live in one place in `internal/platform/queue`: `MaxRetry(5)`, a jittered exponential retry delay (base 1 s, ±20 %), and task timeouts. Producers do not re-declare them.
- The worker composition root mirrors `cmd/api`: config, logger, DB/Redis opens without dialing (Redis parses), signal handling with a drain, no migrations, `os.Exit(runMain())`.
- Probes reuse `internal/platform/health` + `httpx` on a small internal listener; readiness = DB ping + Redis ping (+ queue client check), liveness = plain 200. No contract surface changes (the worker is not contract-tested; it has no HTTP routes in the snapshot).
- Tests use miniredis; the enqueue→consume path is exercised with a test handler through the platform client/server pair. The retry delay function is unit-tested for monotonic growth and jitter bounds.

## Impact Areas

- API / contract: no (no new operations; allowlist untouched)
- DB / migrations: no
- Auth / session: no
- Config / secrets: reuse `REDIS_URL`/`DATABASE_PATH`; new knobs only if the reference has them (`QUEUE_*` — the reference keeps policy in code, so none)
- Observability: worker logs carry job type, job id, attempt, and the propagated ids
- CI / release: the worker binary joins `make build`/`build-pg` and the build step (`cmd/worker` must compile under both lanes)

## Acceptance Criteria

1. `cmd/worker` boots with valid config: opens DB + Redis without dialing, starts the asynq server, serves `/health` (200) and `/ready` (200 when DB+Redis answer, 503 otherwise), and drains cleanly on SIGINT/SIGTERM.
2. `internal/platform/queue` exposes one producer call and one server-registration surface, both typed: enqueueing a payload with meta and consuming it returns the same payload with `request_id`/`trace_id` available to the handler.
3. Retry policy: failed tasks retry up to 5 attempts with a jittered exponential delay; a unit test pins the growth and the jitter bounds.
4. Worker shutdown waits for in-flight tasks (asynq drain) within a bounded timeout.
5. `make verify` green (worker builds in both lanes; no drift; probes covered by a worker smoke test).

## Decision Log

- 2026-10-13: Job metadata lives inside the JSON payload (`__meta`) rather than asynq task options, so the producer and worker agree on one shape and OTel can slot in later.
- 2026-10-13: Retry/backoff policy is owned by the platform queue defaults, not per job, mirroring the reference's `DEFAULT_JOB_OPTIONS`.
- 2026-10-13: The worker does not migrate; the API remains the migration owner.
- 2026-10-13: No production job type in this slice — the wiring is proven by tests, and 5.2 introduces the first real jobs.

## Verification

```bash
go build ./... && go build -tags pg ./...
go test ./internal/platform/queue/... ./cmd/worker/... -count=1
make verify
```

Outcome: `cmd/worker` boots beside `cmd/api`: it opens the DB (the API still owns migrations) and Redis without dialing, starts an asynq server on the `default` queue with the platform retry policy, serves `/health` + `/ready` on `WORKER_HTTP_PORT`, and drains in-flight jobs and the probe listener on cancel. `internal/platform/queue` owns job/queue name validation, the `__meta` envelope (request/trace ids), `REDIS_URL` parsing (redis:// and rediss://, db index, credentials), the producer with the platform defaults (5 attempts, 30 s timeout), the server with a slog adapter, and the jittered exponential retry delay (1 s base, ±20 %, capped exponent). No production job type yet; 5.2 adds the first.

Verification: queue tests cover name validation, the meta round trip (including a payload without an envelope), `REDIS_URL` parsing (credentials, db index, `rediss` TLS, bad scheme, bad db), retry growth across attempts plus jitter bounds sampled 64× per attempt, an enqueue→consume round trip through a real asynq server on miniredis, and invalid-name rejection. The worker smoke test boots the queue server and probes, asserts `/health` and `/ready` 200, then cancels and asserts a clean shutdown. `golangci-lint run` 0 issues; both build lanes pass; `make verify` full profile green (no generated artifacts changed, so no drift step).

## Completion Notes

Deviations and discoveries: the worker needed its own listener, so `WORKER_HTTP_PORT` (default 8081) joined the config schema and `env.example` — the plan's "no new knobs" line covered queue policy only, and a shared `HTTP_PORT` would collide when both processes run on one host. `plannedPaths` no longer exempts `cmd/worker/`, mirroring the `internal/features/` shrink from N8, with the knowledge test extended to keep it honest. The slice also surfaced a real test bug: `TestGoogleVerifierRejections/tampered` replaced the token's last two base64url characters with `AA`, which is a no-op whenever the token already ends that way — and the final base64url character drops its low bits, so even an A/B swap can decode identically. The helper now flips a mid-signature character and the case passed 100 consecutive runs.
