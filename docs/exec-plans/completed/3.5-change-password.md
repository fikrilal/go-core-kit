# 3.5 — Change password

- Status: completed

## Objective

Ship `auth.password.change` wire-identical to backend-core-kit: the first protected route (guard + idempotency), password policy on the new secret, a compare-and-set credential update, and other-session revocation while the current session stays active.

## Reference (backend-core-kit, exact behaviors)

- **Route**: `POST /v1/auth/password/change`, access-token guarded, `@Idempotent({ scopeKey: 'auth.password.change' })`, optional `Idempotency-Key` header (1–128 chars), **204** on success. Declared codes: `VALIDATION_FAILED`, `UNAUTHORIZED`, `IDEMPOTENCY_IN_PROGRESS`, `CONFLICT`, `AUTH_PASSWORD_NOT_SET`, `AUTH_CURRENT_PASSWORD_INVALID`, `INTERNAL`.
- **Service order**: password policy on `newPassword` → `currentPassword === newPassword` → 400 `VALIDATION_FAILED` `{field: newPassword, "New password must be different"}` → credential missing → 409 `AUTH_PASSWORD_NOT_SET` → verify current → 400 `AUTH_CURRENT_PASSWORD_INVALID` → hash new → CAS update.
- **CAS transaction**: user missing → `not_found` (401 `UNAUTHORIZED`); credential missing → `password_not_set`; stored hash ≠ expected → `current_password_mismatch`; else update the hash, then revoke every *other* active session (clear `active_key`/push fields, set `revoked_at`) and their refresh tokens. The current session is untouched.
- Idempotency sits *inside* the guard, so unauthorized requests never touch the replay store.

## Constraints

- The guard's first live route: compose `guard.Require(router.Idempotent(op, handler))` — a new `Router.Idempotent` accessor exposes the wrapped handler for outer composition (backend's guard-before-interceptor order).
- The handler re-checks the principal (defense in depth, mirroring the reference's `CurrentPrincipal` 401).
- No `database/sql` in feature code; nullable/absent columns through generated types only.
- Revocation queries stay portable (subqueries over `sessions`, no `sqlc.slice`).

## Acceptance Criteria

1. Happy path live: 204, old password refused, new password accepted, the current session's refresh token still rotates while the other session reports `AUTH_SESSION_REVOKED`.
2. Idempotent replay: the same `Idempotency-Key` returns 204 with `Idempotency-Replayed: true`; an unauthorized request carrying a key does not prime the store (guard-outer proves).
3. Problem paths: no token → 401 `UNAUTHORIZED`; wrong current → 400 `AUTH_CURRENT_PASSWORD_INVALID`; identical passwords → 400 `VALIDATION_FAILED` `{field: newPassword}`; short `newPassword` → 400 `VALIDATION_FAILED` `{field: newPassword}`; missing fields → 400; credential removed → 409 `AUTH_PASSWORD_NOT_SET`. All declared codes asserted.
4. Unit tests: policy field naming, identical-password check, missing credential, wrong current, CAS kind mapping, CAS input carries user/session/expected hash.
5. `make verify` green.

## Completion Notes

The CAS update mirrors the reference transaction: user-exists, credential-exists, expected-hash compare, credential update, then other-session revocation (device state cleared, sessions and their refresh tokens revoked) — all in one transaction, with the current session untouched. `Router.Idempotent` exposes the replay wrapper so `guard.Require(router.Idempotent(op, handler))` composes authentication outside the replay store (a Redis lock is never taken for unauthorized requests). Gate-driven fixes: qualified subquery column (sqlc ambiguity), `unconvert`, and the wire-code `gosec` nolint.
