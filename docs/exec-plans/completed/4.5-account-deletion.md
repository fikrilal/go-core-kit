# 4.5 — Account deletion request/cancel

- Status: completed
- Owner: Core kit maintainers
- Risk: medium
- Date: 2026-10-13
- Roadmap: `docs/exec-plans/roadmap.md` Phase 4
- Related ADRs: ADR-0001 (feature tiers), ADR-0005 (portable SQL)

## Objective

`users.me.accountDeletion.request` + `users.me.accountDeletion.cancel` in `internal/features/me`, at parity with backend-core-kit `UserAccountDeletionController` / `AccountDeletionService`, plus the Me view's `accountDeletion` field that both the auth and me slices carry. The final de-identification is 5.4 (worker); the 2-hour/30-day jobs and notification emails are recorded follow-ups. Allowlist 14 → 12.

## Ground truth (read from the reference before writing code)

- Request: `POST /v1/me/account-deletion/request`, optional `Idempotency-Key`, 204, codes `UNAUTHORIZED, IDEMPOTENCY_IN_PROGRESS, CONFLICT, USERS_CANNOT_DELETE_LAST_ADMIN, INTERNAL`. Grace period **30 days**; `scheduledFor = now + 30d`.
  Repository, one transaction: user missing/`DELETED` → `not_found` (401); caller is `ADMIN` **and** `ACTIVE` **and** not already scheduled → count active admins under a lock, `<= 1` → `last_admin` (409 `USERS_CANNOT_DELETE_LAST_ADMIN`, "Cannot delete the last admin"); already scheduled → `already_requested` (204, **no** new audit row, due date stays the stored one); else set `deletion_requested_at`, `deletion_scheduled_for`, `deletion_requested_session_id`, `deletion_requested_trace_id` and write an audit row `REQUESTED`.
- Cancel: `POST /v1/me/account-deletion/cancel`, optional `Idempotency-Key`, 204, codes `UNAUTHORIZED, IDEMPOTENCY_IN_PROGRESS, INTERNAL`. Repository: missing/`DELETED` → `not_found` (401); nothing scheduled → `not_requested` (still 204, no audit); else clear the four columns and write an audit row `CANCELED`.
- Audit: `user_account_deletion_audits(id, actor_user_id, actor_session_id, target_user_id, action REQUESTED|CANCELED, trace_id, created_at)`, indexed by target+created, actor+created, and trace.
- Controller schedules notification emails and the finalize job best-effort — both are worker/queue work (5.4).
- Me view: `MeDto.accountDeletion` is `{requestedAt, scheduledFor}` or null, present in every Me-bearing response (auth register/login/refresh/exchange and `users.me.get`); the reference's `MeService.toMeView` derives it from the two user columns.

## Constraints

- The four deletion columns land on `users`; the Me read is the shared `GetMeView` query, so auth's domain/mapping and me's mapping both gain the field — a deliberate cross-slice touch justified by the contract.
- The active-admin count runs inside the write transaction; SQLite serialises writers, and the pg lane's `FOR UPDATE` + retry is recorded with the other pg follow-ups.
- Notifications and the finalize scheduler stay out (no queue): 204 first, jobs later (5.4).
- Trace id comes from `X-Request-Id`; empty values are stored as NULL via the house `NULLIF` pattern.

## Impact Areas

## Acceptance Criteria

1. Request → 204; `GET /v1/me` then carries `accountDeletion` with `scheduledFor` = now + 30 days and `requestedAt` set; one audit row `REQUESTED`.
2. Repeat request (with and without an `Idempotency-Key`) → 204, the due date is unchanged, and no second audit row is written.
3. Cancel → 204, `accountDeletion` disappears from Me, one audit row `CANCELED`; cancel with nothing scheduled → 204 without a CANCELLED row.
4. The only active admin requesting deletion → 409 `USERS_CANNOT_DELETE_LAST_ADMIN`; an admin with another active admin → 204.
5. Deleted users → 401; missing tokens → 401 on both routes; replay with the same `Idempotency-Key` returns the cached 204 with `Idempotency-Replayed: true`.
6. `make verify` green; generated code committed.
