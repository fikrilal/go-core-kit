# 3.4 — Access tokens: verifier, principal guard, and JWKS endpoint

- Status: completed
- Owner: Core kit maintainers
- Risk: high
- Date: 2026-10-11
- Roadmap: `docs/exec-plans/roadmap.md` task 3.4
- Related ADRs: ADR-0002 (parity)

## Objective

Complete the access-token surface: publish the public keys at `/.well-known/jwks.json` (`auth.jwks.get`), verify tokens with the reference's exact claim rules, and provide the principal guard the first protected routes will mount.

## Reference (backend-core-kit, exact behaviors)

- **JWKS**: `GET /.well-known/jwks.json` returns a non-enveloped `{keys: [...]}` document; every usable key in the configured set is published as `{...publicJwk, kid, use: "sig", alg}`; private material never leaves the process.
- **Verification order**: token length ≤ 16384 → parse three JSON segments → `kid` + `alg` from the header, key must exist for the kid and its alg must match → signature → `exp` present and future → `iat` present and no more than 60s in the future → `iat ≤ exp` → optional `nbf` (≤ now+60, ≤ exp) → `iss`/`aud` matches when configured → `typ == "access"` → `sub`/`sid`/`jti` present, `jti ≤ 128` → principal `{userId, sessionId, emailVerified, roles}` (roles: string items only, trimmed, deduped).
- **Guard**: `Authorization` scheme compare is case-insensitive; missing/invalid token → 401 `UNAUTHORIZED` problem; unexpected verification errors surface as 500 `INTERNAL` through the central mapper.
- **Misconfiguration**: staging/production require `AUTH_ISSUER` and `AUTH_AUDIENCE` (verifier construction fails otherwise).

## Constraints

- The JWKS document is not enveloped — a new `httpx.Document` helper keeps features out of raw JSON (depguard stays satisfied).
- Features keep their boundary: the platform returns a marshalable `auth.JWKS` type, so the feature never imports `jwk`.
- The guard has no live consumer until the first protected route (3.5); it is unit-tested against an `httptest` server, not wired as dead composition.
- All verification failures return the `ErrInvalidToken` sentinel; the guard maps only that sentinel to 401.

## Acceptance Criteria

1. JWKS live test: 200, snapshot-validated, publishes the signing key's public JWK with `kid`/`use`/`alg` and no private material; allowlist shrinks.
2. Verifier tests: signed-token round trip; every rejection rule from the reference order (length, malformed, unknown kid, alg mismatch, tampered signature, expired, future `iat`, `iat > exp`, `nbf`, `iss`, `aud`, `typ`, missing `sub`/`sid`/`jti`, long `jti`); roles parsing; production-like misconfiguration error.
3. Guard tests: valid token attaches the principal (`PrincipalFrom`); missing header, wrong scheme, and invalid tokens return the 401 `UNAUTHORIZED` problem with a trace id.
4. End-to-end: a token issued by register verifies against the same keyring with matching claims.
5. `make verify` green.

Outcome: `/.well-known/jwks.json` is live — 200, snapshot-validated, publishes the signing key as `{kid, kty: OKP, crv: Ed25519, use: sig, alg: EdDSA}` with no private material. The verifier's rejection matrix passes: empty/garbage/oversized tokens, tampered signature, unknown kid, alg mismatch, signature from another key, expired, future `iat`, `iat > exp`, future `nbf`, issuer/audience mismatch (and array-audience acceptance), wrong `typ`, missing `sub`/`sid`/`jti`/`exp`, over-long `jti`, plus non-boolean `email_verified` and role sanitization. The guard attaches the principal (validated through the router chain, so 401 problems carry trace ids) and rejects missing/wrong-scheme/tampered credentials with the `UNAUTHORIZED` problem. End-to-end: a register-issued token verifies against the same keyring with matching user/session claims; a tampered token is rejected. Coverage: 7 implemented / 27 allowlisted / 34 declared. Race-clean; `make verify` green except drift-until-commit.

## Completion Notes

Gate-driven decompositions: `KeyRing.addKey` (per-key publication), `Verifier.verifiedPayload` + `principalFromClaims` (signature vs claim rules), and a guard-test assertion helper. The guard is composed at registration (`guard.Require(handler)` inside the router), so platform middleware supplies the request id before authentication runs. Tests use a deterministic tamper helper (flipping the first signature character) after a 1-in-64 flake when simply forcing `A`. `httpx.Document` is the single non-enveloped response path (JWKS today; OIDC discovery or well-known documents later).
