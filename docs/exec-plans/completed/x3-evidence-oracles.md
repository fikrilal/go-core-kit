# x3 — Evidence and oracles for runtime flows

## Objective

Back runtime claims with artefacts instead of prose. Two flows have earned it: the
HTTP surface, where the contract suite already drives every operation, and the job
lanes, whose outcomes are a matrix of skips and effects that tests assert one case
at a time.

## Deliverables

1. **Golden captures for the wire surface.** The contract suite records each
   operation's response shape (status, envelope keys, problem code where the case
   is a refusal) into `cmd/api/testdata/golden/<operation>.json`, and compares
   against it on later runs. Regenerate with a documented flag. This is the
   artefact a wire-contract change is reviewed against.
2. **A job-outcome oracle.** The skip/effect matrix — missing user, deleted
   account, revoked session, not-due re-arm, last-admin block, sent email — becomes
   a table shared by the handler tests and the worker tests, so a new skip is a row
   rather than a new test, and the matrix is readable in one place.
3. A short section in `docs/standards/testing-strategy.md` describing both, and how
   to regenerate the captures.

## Acceptance checks

1. A wire change that alters an envelope without touching the operation's declared
   shape fails the golden comparison with a diff naming the operation.
2. The oracle table drives both the app-level and worker-level assertions, and
   adding a row without implementing it fails.
3. `make verify`, `make verify-pg`, and the scaffold smoke stay green; the goldens
   are regenerated by the documented flag rather than edited by hand.

## Progress — the shape oracle (2026-10-17)

**Deliverable 1 is landed.** 25 call sites are wired across the contract suite and 21
captures are recorded; both the update and the compare path pass, and the captures are
stable across runs. The sweep found two things worth knowing: keying by path alone
collides because one route answers several ways (status and problem code are part of
the name now), and a route with a generated id in its path (`/sessions/<uuid>/revoke`)
mints a new file per run unless identifier segments are normalized (`_id_`).

What follows was written before those findings; the mechanism it describes is what
shipped. `assertGoldenShape` (`cmd/api/golden_test.go`)
captures an operation's wire shape — status, envelope keys sorted, problem code —
into `cmd/api/testdata/golden/<operation>.json`, and compares on later runs;
`-update-golden` regenerates. Values are excluded on purpose, so the oracle catches
contract drift rather than data churn. Four operations are wired as the proof:
`auth.email.verify` (a 204 with no body), `users.me.get` (the `data` envelope),
`users.me.sessions.list` (envelope plus `meta`), and
`users.me.accountDeletion.request` (another bodyless 204). Captures were written and
the compare path passes; `docs/standards/testing-strategy.md` documents the
mechanism and the regeneration command.

**Still open in this slice:**

- **Deliverable 2, the job-outcome oracle.** The skip/effect matrix (missing user,
  deleted account, revoked session, not-due re-arm, last-admin block, sent email) as
  one table driving both the app-level and the worker-level assertions. The open
  question is placement: a test-only table cannot be imported by the worker's test
  package if it lives in a `_test` file, and shipping test data in a production
  package is the wrong trade. The kit's precedent is `internal/platform/dbtest` — a
  small non-test package that exists for tests — so the oracle likely belongs beside
  the jobs it describes (`internal/features/auth/oracle` or similar) rather than
  inside either test package. That decision needs to be made before the code, which
  is why it is recorded here rather than improvised.

## Outcome — landed 2026-10-17

Both deliverables are in.

**The shape oracle** covers every response the contract suite validates: 25 call
sites, 21 captures under `cmd/api/testdata/golden/`, keyed by route path with
identifier segments normalized, and including the status and problem code in the name
so one route's success and refusals each get their own capture. Regenerate with
`go test ./cmd/api -update-golden`.

**The job-outcome oracle** lives in `internal/features/auth/oracle` as data: the
account states (`missing`, `deleted`, `suspended`, `active`), what each email handler
must report, and whether it may send. The placement question this plan raised is
answered by the kit's own precedent — a small non-test package, importable by both
suites, rather than test data in a production package or a table locked inside a
`_test` file. The feature's tests assert outcomes from it; the worker's test asserts
effects from it (an email leaves, and a token is minted, only for the states the
matrix says send). A rename of an outcome now fails in both places at once.

Deliberately outside the matrix: the "already verified" skip, which is a property of
the verification timestamp rather than an account state, and the push and cleanup
jobs, whose state machines are larger and worth their own matrices if they need them.

Verification: `golangci-lint run` 0 issues, the full suite green, `make verify` full
profile passed, `make verify-pg` passed.

## Review round 1 — findings recorded, not yet fixed (2026-10-17)

An independent review of the commits that landed this slice confirmed the mechanism
works and found four gaps in it. They are recorded here because they would otherwise
disappear with the review transcript:

- **`States()` can drift from the matrices.** It is a hand-written slice while
  `Verification` and `PasswordReset` are separate maps, so adding a row to a matrix
  without editing `States()` leaves it unasserted — the drift the oracle exists to
  prevent, and the reason this plan's acceptance check 2 is not yet met. Derive
  `States()` from the matrices, or assert that every key appears in it and that both
  matrices share a key set.
- **The golden key ignores the HTTP method.** `GET /v1/me` and `PATCH /v1/me` share
  `v1.me.200.json`, so today they are one oracle entry: a shape change in either fails
  the other's test. Include the method in the name.
- **An orphan capture is committed.** `.well-known.jwks.json.json` is byte-identical
  to `.well-known.jwks.json.200.json` and is never read; `-update-golden` never prunes,
  so a renamed route leaves its old file behind. Delete it, and consider asserting that
  every file under `testdata/golden` was read.
- **The refusal half is advertised but unwired.** No capture contains a `code`, so a
  wrong error code on a 4xx is still not caught, and the counts in this plan
  (25 call sites, 21 captures) are the plain-`ls` numbers: the tree holds 23 golden
  files, 22 live keys plus the orphan, and 26 `ValidateResponse` call sites — the
  26th being the health-probe loop, deliberately outside the sweep.

Also noted: `Verification` and `PasswordReset` are currently identical maps, which the
duplication standard landed in the same range would call two copies of one decision;
data literals are invisible to `dupl`.
