# 3.6 — Email verification + resend

## Objective

Implement the two contract operations that complete the verification loop whose
worker half landed in 5.2: `auth.email.verify` and
`auth.email.verification.resend`. With them the allowlist drops from 12 to 10 and
Phase 5's exit gate takes its first step (3.7 is the second).

## Contract (from the pinned snapshot)

**`POST /v1/auth/email/verify`** — public, body `VerifyEmailRequestDto`
(`token` required), `204`, unauthenticated. Error codes: `VALIDATION_FAILED`,
`AUTH_EMAIL_VERIFICATION_TOKEN_INVALID`, `AUTH_EMAIL_VERIFICATION_TOKEN_EXPIRED`,
`INTERNAL`.

**`POST /v1/auth/email/verification/resend`** — authenticated (`access-token`),
no body, `204`. Error codes: `UNAUTHORIZED`, `RATE_LIMITED`, `INTERNAL`; the
snapshot's description names it as rate limited.

## What already exists

- 5.2's worker job `auth.sendVerificationEmail` mints the token (hash-stored,
  24 h TTL) and sends the email through the `emails` lane. The API never mints
  tokens; it enqueues.
- `db/queries/common/auth.sql` has `VerifyUserEmailIfUnset` (added for OIDC in
  3.10) and `CreateEmailVerificationToken`.
- `auth`'s app already carries a `LoginLimiter` port (`AssertAllowed` /
  `RecordFailure`) used by login, which is the shape the resend limiter should
  follow.

## Design

**New query** — consume one verification token by hash:
`ConsumeEmailVerificationToken :one` selecting the token row by `token_hash`
where the token is unused and unrevoked, joined to the user for status, returning
the user id, `expires_at`, and the account status. Consumption is a compare-and-
set update (`MarkEmailVerificationTokenUsed :execrows`), so two concurrent
verifies cannot both succeed.

**Verify use case** — hash the presented token, load it, then:
- unknown hash → `AUTH_EMAIL_VERIFICATION_TOKEN_INVALID`;
- expired (or used) → `AUTH_EMAIL_VERIFICATION_TOKEN_EXPIRED`;
- account `DELETED` → the invalid code (an unverifiable account must not learn
  anything);
- otherwise mark the token used and `VerifyUserEmailIfUnset`, then 204. Verifying
  an already-verified account is a success (204), not an error, mirroring the
  reference's idempotence.

**Resend use case** — guarded; requires a session. Ordering follows the kit's
rule: body/route validation → provider gate → account state → rate limit →
enqueue. A resend when the account is missing or `DELETED` answers 204 without
enqueuing (no oracle), a suspended account may resend, and when email is not
configured the route answers `501` through the same gate the auth feature already
uses for unconfigured providers.

**Rate limit** — per user id on the resend route, `429 RATE_LIMITED` with
`Retry-After`, reusing `platform/redis` keyed like the login limiter. Config knobs
follow the existing pattern (`AUTH_EMAIL_RESEND_*`), documented in env.example
and validated at load.

**Why enqueue rather than mint here** — the kit decided in 5.2 that the job owns
token minting, so the API cannot mint a token it does not send. A failed enqueue
is a real failure and surfaces as `INTERNAL`; there is no partial state to
compensate because nothing was written.

## Acceptance checks

1. Verify: valid token → 204 and the account is verified; replayed token → the
   expired/invalid problem; expired token → its own code; unknown token → the
   invalid code; malformed body → `VALIDATION_FAILED` with a `token` field issue.
2. Resend: authenticated → 204 and a job lands on the `emails` lane with the
   `queue.Meta` envelope; over the limit → `429` with `Retry-After`; without a
   session → `401`; with email unconfigured → `501`.
3. Both operations leave the allowlist and the coverage test stays green;
   `make verify` passes.
4. Contract tests in `cmd/api` cover the happy path plus each problem above.

## Notes and risks

- The token hash algorithm must match 5.2's minting exactly (SHA-256 over the
  presented token, hex); a mismatch would make every verification fail, so the
  first test asserts a token minted by the worker-side query verifies.
- 3.7 reuses this shape: `auth.password.reset.request` (public, body `{email}`,
  enqueue only, no oracle) and `auth.password.reset.confirm` (public, body
  `{token, password}`, set the credential and revoke sessions). Its code list and
  DTO fields still need extracting from the snapshot; the plan for 3.7 should
  reuse `ConsumePasswordResetToken` and the same limiter and gating decisions.

## Progress — 2026-10-15 (increment 1: the verify use case)

  `db/queries/common/auth.sql`, with `ports.EmailVerificationTokenState` and the
  `EmailVerificationTokenByHash` / `ConsumeEmailVerificationToken` repository

  verify.

Recorded decisions: an empty token is the DTO's `required` validation rather than
a service branch, and the token hash comes from
`domain.HashEmailVerificationToken`, the same helper the 5.2 job mints with.

## Review round 1 — fixes (2026-10-15)

- **Atomicity (High).** Consumption and verification now share one transaction:
  `ConsumeEmailVerificationTokenAndVerifyEmail` runs
  `MarkEmailVerificationTokenUsed` and `VerifyUserEmailIfUnset` inside `InTx`, so a
  failure can no longer spend a token without verifying its address. The two
  separate repository methods are gone.
- **Dual-engine parity (Low).** `sqlc.yaml` now overrides the 0006 token columns
  for the `postgresql` engine as well as `sqlite`, so `used_at` is `utctime.Time`
  in both lanes rather than `sql.NullTime` on PG.
- **Scaffold defects (Critical, from the same review).** The composition root had
  two `// gokit:feature-registrations` markers, so scaffolded features were
  inserted before `guard` existed and `make scaffold-smoke` failed; there is now
  exactly one marker, after the guard. `scaffold endpoint` also re-declared
  imports and the `handlers` struct when a second endpoint landed on the same
  feature, and `operationSlug` collapsed `reports.list` and `reports.get` onto one
  file name: slugs and symbols now carry the resource *and* the verb, both paths
  are covered by a two-endpoint test, and the test fixture's marker mirrors the
  real composition root so the scoping defect cannot return unnoticed. The smoke
  was re-run after the fixes and reports `passed — scaffolded output is
  gate-clean`.
- **Scope (Medium).** The half-plumbed resend dependency seam — knobs,
  `queue.Scheduler.EnqueueAt`, the feature's `JobScheduler` port, the `Deps` and
  `Service` fields, and `CodeAuthEmailNotConfigured` — was reverted rather than
  left dead. The design above stands as the specification for the slice that
  implements it, so re-landing is mechanical.

## Outcome — landed 2026-10-15

Both operations are implemented and covered:

- **`auth.email.verify`** (public): token consumption and verification share one
  transaction (`ConsumeEmailVerificationTokenAndVerifyEmail`: a compare-and-set
  mark-used plus `VerifyUserEmailIfUnset` inside `InTx`), with the invalid code for
  unknown tokens and unverifiable accounts and the expired code for used, expired,
  or race-lost tokens. Covered by unit tests for each outcome plus a contract test
  asserting the full RFC7807 problem and the echoed request id.
- **`auth.email.verification.resend`** (guarded): the service applies the gates —
  provider configured (else `501 AUTH_EMAIL_NOT_CONFIGURED`), account present and
  not deleted (else a silent success with nothing enqueued), then the per-account
  limiter (`429 RATE_LIMITED`) — and the route enqueues
  `auth.sendVerificationEmail` on the `emails` lane through the feature's own
  `JobScheduler` seam with the request's `queue.Meta`. `auth.email.verification.resend`
  left the allowlist (12 → 10), and a contract test covers the anonymous rejection
  and the unconfigured-provider answer.

Config: `AUTH_EMAIL_RESEND_MAX_ATTEMPTS|WINDOW_SECONDS|BLOCK_SECONDS`, documented
and validated beside their login siblings; the API forwards the scheduler and the
email gate through `authDeps`, keeping the interface nil — never a typed nil —
when `REDIS_URL` is unset.

Deliberately not claimed: the wire-level "204 and a job is enqueued" path is
covered by the service tests and the worker's registration test rather than a
contract test, because that fixture configures no queue. Recorded as the next
thing to strengthen if the route's enqueue path needs wire coverage.

Verification: `go test ./...` green, both engine lanes build, `golangci-lint run`
0 issues, `make scaffold-smoke` passed, `make verify` green except the
uncommitted-drift step.

## Review round 2 — fixes (2026-10-15)

- **The silent skip enqueued anyway (High).** The handler enqueued whenever the
  service returned no error, so a missing or deleted account — whose check answers
  success by design — still put a job on the lane, and the account check ran before
  the limiter, so those callers were unmetered. `ResendVerificationEmail` now
  reports `(shouldEnqueue bool, err error)`; the limit applies first so every
  attempt counts and the answer never depends on whether the account exists, then
  the account check decides whether the route enqueues. Tests assert the flag on
  every path and that the service itself never enqueues.
- **The limiter lied and shared a namespace (Medium).** Reusing the login limiter
  meant resend answers carried "Too many login attempts" and hashed account ids
  into `auth:login:*`. `infra.NewLimiter` now takes a `LimiterConfig` with its own
  scope and detail, `NewLoginLimiter` delegates with the login values unchanged,
  and the resend lane uses `auth:email_resend` with its own message.
- **Flag parsing could misread a value as a flag (Low).** The inner name loop kept
  scanning after a match, so `--feature --operation` could consume the wrong token;
  it now breaks on the first match, with router tests covering both new commands
  and their usage errors.
- **Nits.** The resend contract test's dead marshal is gone.

## Review round 3 — fixes (2026-10-15)

- **The limiter's scope was dead (High).** Round 2 parameterized the message but
  `keys()` still hardcoded `auth:login`, so resend attempts were counted into the
  login counters — exhausting the resend limit would have blocked that account's
  password logins, and vice versa. `keys()` now builds its namespace from the
  configured scope, and `TestLimiterScopesAreIsolated` proves an exhausted resend
  lane still allows a login for the same subject.
- **The resend success path had no live contract test (Medium).** The guarded route
  is now exercised end to end with a sender configured and a queue present: the
  first call answers `204` and validates against the snapshot, the second answers
  the declared `429 RATE_LIMITED`. Getting there needed the fixture to expose a
  queued variant — setting `REDIS_URL` for every fixture broke the me deletion
  tests, which rely on scheduling being unconfigured — so `newAuthFixtureWithQueue`
  scopes the queue to the tests that need it.
- **A second endpoint dropped its query (Low).** `scaffold endpoint` now appends to
  the feature's `db/queries/common/<feature>.sql` instead of discarding the
  template, so the generated repository stub's query actually exists.
- **Port methods are declared by hand (Low).** The generator leaves
  `ports.Repository` as the feature's own boundary; plan 6.1 and
  `docs/guide/adding-an-endpoint.md` now say so instead of claiming otherwise.
