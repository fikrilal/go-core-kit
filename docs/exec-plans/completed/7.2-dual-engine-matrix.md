# 7.2 — Dual-engine CI matrix

## Objective

Run the suites on both engines in CI, so the SQLite lane's green means nothing
without the pg lane's green beside it: integration, contract, and the
schema-inventory drift.

## Landed

- A `verify-pg` CI job with a Postgres service, running `make verify-pg`
  (`fmt-check-pg`, `vet-pg`, `lint-pg`, `test-pg`, `build-pg`), so the pg lane is
  built, vetted, linted, and tested on every push.
- The lane's integration test runs **live** when `DATABASE_URL` is set:
  `TestPGRoundTrip` applies the pg migrations, commits a transaction, and rolls one
  back. Verified locally against a `postgres:17` container: it passes.
- `internal/platform/dbtest` gives tests a database per lane: a temporary SQLite
  file, or a **schema of its own** inside the server `DATABASE_URL` names, dropped
  on cleanup. `dbtest.Rebind` converts the portable `?` placeholders to the lane's
  style, so one query text can serve both engines.
- The schema-inventory test already holds the two migration trees to the same
  table and column names, so drift between them fails the SQLite lane today.

## Outcome — landed 2026-10-15

The contract suites run on the pg lane. What it took, in the order the live server
demanded it:

1. **A portable placeholder story.** `dbtest.Rebind` for tests and `db.Rebind` on
   the platform — one implementation per lane — so hand-written SQL reads the same
   on both engines. The pg lane's hand-built me-sessions page query needed it too:
   it failed with `syntax error at or near "ORDER"` until the assembled text went
   through `Rebind`.
2. **A rewrite tool that cannot mangle SQL.** Text-level wrapping corrupted files
   twice, so the call sites were rewritten with a small AST program (`go/parser` +
   `format.Node`) that wraps the second argument of `QueryRowContext`,
   `QueryContext`, and `ExecContext` and never touches string contents. It is
   idempotent, and running it again caught the sites the first pass missed — the
   ones behind computed query arguments.
3. **State isolation per test.** `dbtest.Open` gives each test its own Postgres
   schema, migrated from the pg tree and dropped on cleanup, with the admin handle
   now outliving `Open` so the drop can happen.

Verified against a live `postgres:17` container:
- `TestPGRoundTrip`: migrations, commit, rollback — pass.
- The **whole `cmd/api` contract suite** under `-tags pg` with `DATABASE_URL` set —
  pass (12.6s), including auth, refresh/logout, email verify/resend, password
  change/reset, me push, profile image, sessions, and deletion.
- `make verify` on the SQLite lane unchanged; `make verify-pg` passes with the
  server up and the guarded tests running instead of skipping.

Remaining tagged paths are the lanes' own tests (4), listed in the audit note: they
assert engine-owned behaviour and do not lift.

## Acceptance checks

1. `make verify-pg` passes **with** `DATABASE_URL` pointing at a server, exercising
   the contract suites against Postgres rather than skipping them.
2. The SQLite lane is unchanged: `make verify` passes with the same suites.
3. The portable-subset counts move down as the tags lift, and the audit note moves
   with them.
4. `dbtest.Open` isolates state per test: no test sees another's rows, and the
   schemas are dropped afterwards.

## Notes

- Local Postgres comes from `docker run -d --name gokit-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=gokit -p 55432:5432 postgres:17`,
  with `DATABASE_URL=postgres://postgres:postgres@localhost:55432/gokit?sslmode=disable`.
  The container is throwaway: stop it after the run.
- The pg lane's migrations run per test schema, so migration cost is paid per test;
  if that becomes slow, the harness can migrate one template schema and clone it.
