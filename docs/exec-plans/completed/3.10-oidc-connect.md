# 3.10 — `auth.oidc.connect`

- Status: completed
- Owner: Core kit maintainers
- Risk: medium
- Date: 2026-10-12
- Roadmap: `docs/exec-plans/roadmap.md` Phase 3, allowlist group "Phase 3 — auth slice"
- Related ADRs: ADR-0001 (feature tiers), ADR-0003 (HTTP behavior), ADR-0006 (Redis), ADR-0007 (config/secrets)

## Objective

Implement `POST /v1/auth/oidc/connect` at parity with backend-core-kit: link a verified Google identity to the authenticated user, mark the account email verified when the identity email matches and the account is still unverified, and report the two conflict shapes distinctly. Guarded, idempotent (guard outside the replay store). Allowlist 25 → 24.

## Ground truth (read from the reference before writing code)

Backend `oidc.controller.ts` + `oidc-auth.service.ts` `connectOidc`:

1. `requireExistingNonDeletedUser(userId)` first: missing or `DELETED` → 401 `UNAUTHORIZED`. `SUSPENDED` **passes**.
2. Verify the id_token (shared helper): `not_configured` → 500 `AUTH_OIDC_NOT_CONFIGURED`; `invalid` → 401 `AUTH_OIDC_TOKEN_INVALID`; `!emailVerified` → 400 `AUTH_OIDC_EMAIL_NOT_VERIFIED`.
3. `linkExternalIdentityToUser({userId, provider, subject, email, now})` in one transaction (`prisma-auth.repository.users.ts`):
   - user missing → `user_not_found` (→ 401 `UNAUTHORIZED`).
   - identity by `(provider, subject)` found: owned by another user → `identity_linked_to_other_user` (409 `AUTH_OIDC_IDENTITY_ALREADY_LINKED`); owned by this user → `verifyEmailIfMatching`, then `already_linked` (204).
   - this user already has a link for the provider → `provider_already_linked` (409 `AUTH_OIDC_PROVIDER_ALREADY_LINKED`).
   - create identity (`NULLIF` on the email); unique violation → re-read in both directions (`identity_linked_to_other_user` / `already_linked` / `provider_already_linked`), else rethrow.
   - `verifyEmailIfMatching`: identity email non-empty AND equals the account email AND `email_verified_at` still null → set it (conditional `UPDATE ... WHERE email_verified_at IS NULL`).
   - `ok` / `already_linked` → 204, no body.
4. Connect never touches the profile (that is exchange's `createUserWithExternalIdentity`).

Snapshot: `POST /v1/auth/oidc/connect`, optional `Idempotency-Key` header, request `OidcConnectRequestDto {provider, idToken}`, response 204, security `access-token`, declared codes `VALIDATION_FAILED, UNAUTHORIZED, IDEMPOTENCY_IN_PROGRESS, CONFLICT, AUTH_OIDC_NOT_CONFIGURED, AUTH_OIDC_TOKEN_INVALID, AUTH_OIDC_EMAIL_NOT_VERIFIED, AUTH_OIDC_IDENTITY_ALREADY_LINKED, AUTH_OIDC_PROVIDER_ALREADY_LINKED, INTERNAL`.

## Constraints

- Two call sites (exchange + connect) justify one shared private verifier helper in `app`; it mirrors the reference's `verifyOidcIdentityOrThrow` and maps exactly the three failures, verified continues.
- Problem helpers stay in `app/problems.go`; handlers stay dumb.
- New SQL goes in `db/queries/common/auth.sql`; `GetUserByID` stays the narrow existence query (do not widen it).
- No new config, no route wildcard, no auto-linking.

## Acceptance Criteria

1. `POST /v1/auth/oidc/connect` with a valid token links the identity and returns 204 for `ok` and `already_linked`; replay with the same `Idempotency-Key` returns 204 + `Idempotency-Replayed: true`.
2. Identity owned by another user → 409 `AUTH_OIDC_IDENTITY_ALREADY_LINKED`; same user, different subject → 409 `AUTH_OIDC_PROVIDER_ALREADY_LINKED`.
3. Identity email equal to an unverified account email → `email_verified_at` set; different email → left null.
4. Deleted user → 401 `UNAUTHORIZED` before verification; suspended user proceeds (reference parity).
5. Invalid token → 401 `AUTH_OIDC_TOKEN_INVALID`; `email_verified` false → 400 `AUTH_OIDC_EMAIL_NOT_VERIFIED`; provider not configured → 500 `AUTH_OIDC_NOT_CONFIGURED`.
6. UNAUTHORIZED requests never prime the idempotency store (guard outside).
7. `make verify` green; `make generate` produces no drift.

## Completion Notes

Extraction note: `verifyOidcIdentity` was created only when the second call site appeared (connect joins exchange), mirroring the reference's shared `verifyOidcIdentityOrThrow`. The reference's pre-check order was preserved deliberately — a deleted account with an invalid token is 401 `UNAUTHORIZED`, not 401 `AUTH_OIDC_TOKEN_INVALID`, and no JWKS fetch happens for it. The transaction keeps the reference's unique-violation re-read even though SQLite runs a single connection; that path is untestable here and exists for pg parity. `GetUserByID` stayed narrow; the link flow reads `GetUserStatus` and `GetUserForIdentityLink` instead.
